Storage & data modeling

Files, formats, and tables at ten billion rows a day

Panel 2 lists "data modeling and query design for very large datasets". Most of that answer lives below the query, in how bytes are laid out on object storage. This is the layer neither of your repos covers.

Parquet, from the inside

Nearly every "why did this query get faster" question has a Parquet answer, so know the physical layout.

A Parquet file is split into row groups (typically 128 MB–1 GB of rows). Within a row group, each column is stored contiguously as a column chunk, subdivided into pages. The footer holds the schema and, critically, per-row-group and per-page statistics: min, max, null count for each column.

Three consequences you should be able to state without prompting:

  • Projection pushdown. Selecting 3 of 80 columns reads 3 column chunks and skips the rest. Columnar layout is what makes SELECT * genuinely expensive relative to naming columns — on a wide event table, often 20×.
  • Predicate pushdown via statistics. A filter on price > 100 lets the reader check each row group's max and skip entire row groups. This only works if the data is sorted or clustered on that column — on randomly ordered data every row group's min/max spans the full range and nothing is skipped. This is the single most useful insight in the section.
  • Encoding. Dictionary encoding for low-cardinality columns, run-length encoding for sorted repeated values, bit-packing for small integers. Sorting by a low-cardinality column before writing improves both compression and skipping.
The layout insight to volunteer

Sort order at write time determines what can be skipped at read time. Clustering the table on the columns people actually filter by is usually a bigger win than any query rewrite.

From first principles

Start from the physical constraint: reading from object storage costs a network request plus bytes transferred, and the request overhead is significant. So the only two ways to make a scan faster are to read fewer bytes and to make fewer requests.

Columnar layout addresses the first. If a query touches 3 of 80 columns and the columns are stored contiguously, you read roughly 3/80 of the bytes. Row-oriented storage cannot do this, because the columns you want are interleaved with the ones you don't at every row.

Statistics address it differently — not by reading less of each row group, but by skipping whole ones. And that is why the second mechanism is fragile in a way the first isn't: projection always works, because layout is a property of the file, whereas skipping only works if the values happen to be clustered. Same footer, same statistics, completely different outcome depending on write-time sort order.

Why directories aren't enough: table formats

Hive-style tables are just directories of files, and the limitations are severe at scale: listing millions of files is slow, there are no atomic multi-file commits, concurrent writers corrupt each other, schema changes are unsafe, and there is no way to update or delete a row.

Table formats — Apache Iceberg, Delta Lake, Apache Hudi — solve this by putting a metadata layer over the files.

  • Metadata as a tree of manifests. A snapshot points to manifest lists, which point to manifests, which list data files with their column statistics. Query planning reads metadata instead of listing storage, and can prune files before touching them.
  • ACID by atomic pointer swap. A commit writes new data files, then atomically updates the table's current-snapshot pointer. Readers see either the old or new state, never a half-written one. Concurrent writers use optimistic concurrency and retry on conflict.
  • Time travel. Old snapshots remain valid, so you can query the table as of a timestamp or version. Enormously useful for reproducing a model's training set or debugging a bad backfill.
  • Schema evolution by column ID rather than by position or name, so renames and reorders don't corrupt old files.
  • Row-level changes. Copy-on-write rewrites affected files (fast reads, slow writes); merge-on-read writes delete/update files merged at query time (fast writes, slower reads). The choice is a read-vs-write trade-off you should name explicitly.

Partition evolution is Iceberg's distinctive one: because partitioning is metadata rather than directory structure, you can change the partition scheme without rewriting history. Hidden partitioning also means queries filter on the raw column and the engine derives the partition — no more forgetting to add WHERE dt = alongside WHERE event_time =.

Choosing a partition scheme

Partitioning is the highest-leverage modeling decision and the easiest to get wrong in both directions.

Too coarse (partition by month) and every query scans far more than it needs. Too fine (partition by hour and campaign) and you get millions of tiny partitions, metadata bloat, and small files.

A workable heuristic: partition by the column that appears in nearly every query's filter — almost always time — at a granularity that yields partitions in the low hundreds of MB to a few GB. Then use clustering / sort order (Iceberg sort orders, Delta Z-ordering or liquid clustering) for secondary filter columns, rather than adding partition levels.

Modeling the three tables you will be asked about

Event / impression log

Append-only, immutable, wide. Keep a stable event_id for idempotency, both event_time (when it happened) and ingest_time (when you received it) — the gap between them is what late data looks like, and you need both to reason about correctness. Partition on event date for query semantics, but keep ingest time so you can find what arrived late and reprocess exactly those partitions.

Metrics / aggregate layer

Pre-aggregated rollups at the grain people query. The design tension is grain: too fine and you haven't saved anything, too coarse and every new question requires a new table. Keep aggregates additive where possible — sums and counts roll up across time; averages and distinct counts do not. Store the sketch, not the distinct count, precisely so it stays mergeable (that is stage 04).

Slowly changing dimensions

Campaign and advertiser attributes change. If you overwrite them (SCD type 1), historical reports silently change when someone renames a campaign. Type 2 — keep versioned rows with valid_from / valid_to — is what lets you reproduce last quarter's report. Interviewers like this because it exposes whether you think about reproducibility.

Point-in-time correctness

This is where storage design and ML meet, and it is a favourite because getting it wrong is invisible in offline metrics.

When you build a training set for an event at time t, every feature must reflect only what was knowable before t. Joining a feature table naively gives you the current value, which may encode the outcome. A model trained on leaked features shows excellent offline performance and fails in production — the classic symptom pair.

The mechanics: an as-of join (temporal join) that, for each label row, takes the most recent feature row with feature_time <= event_time. This requires your feature tables to be versioned by time rather than overwritten — which is exactly why table formats with time travel and SCD-2 dimensions matter for ML, not just for reporting.

Related and worth naming: the feature computed offline in Spark and the feature computed online in serving must use the same logic, or you get training/serving skew. The two standard mitigations are a shared feature definition (one transformation, two execution modes) and logging the features actually used at serving time so you can train on those exact values.

Pushback

Now defend it

Each of these is a real interrupt. Commit to an answer before you reveal — reading the model answer without having tried is how you end up recognising the material but not being able to produce it.

01
You partitioned the impressions table by date. A user runs SELECT count(*) FROM impressions WHERE campaign_id = 'X' and it scans 30 days of data. They ask you to partition by campaign too. Do you?
The requested fix is the wrong fix. Say why, and offer the right one.
What a strong answer covers

No. Campaign cardinality is in the tens or hundreds of thousands, and adding it as a partition level multiplies partitions by that factor — millions of directories, most holding a few kilobytes. Planning cost and small-file overhead would make every query slower to fix one.

The right mechanism is clustering: sort or Z-order the data within each date partition by campaign_id. Then the file-level min/max statistics let the engine skip most files for a single-campaign filter, giving nearly the same pruning without partition explosion.

I'd also ask why the query is unbounded in time. A count over all history for one campaign is usually better served by the pre-aggregated daily metrics table, which is orders of magnitude smaller. Often the real problem is that the user doesn't know the aggregate table exists.

Then they push again

They insist. They own the downstream product and this query is on their critical path.

Then I'd make the trade-off explicit and offer a scoped compromise rather than either capitulating or blocking. Concretely: I'd quantify it — show what partition-by-campaign does to planning time and file count on a sample, so we're arguing about numbers rather than opinions. Then I'd offer the targeted solution: a dedicated campaign-partitioned aggregate table serving their access pattern, kept small, without restructuring the raw impressions table that everyone else depends on. That gives them the latency they need and preserves the shared table. If they still want it on raw, I'd want the decision recorded with the projected cost, because the person who inherits the pipeline should be able to see why it looks like that.

02
Iceberg or Delta? Pick one and justify it.
There is no right answer. There is a right way to reason.
What a strong answer covers

I'd start by saying the choice matters much less than most comparisons imply — both give ACID commits, time travel, schema evolution, and file-level pruning, and both are converging on the same feature set.

The differentiators worth naming: Iceberg has genuine partition evolution and hidden partitioning, which matter if you expect the partition scheme to be wrong initially — and it usually is. Delta is more deeply integrated with Databricks tooling and has historically been smoother there. Hudi's distinctive strength is incremental upsert-heavy ingestion with record-level indexes.

In practice the deciding factors are usually organisational: what your query engines support, what your team already runs, and what your vendor relationship is. I'd pick Iceberg for engine neutrality on a multi-engine stack, and Delta without hesitation on a Databricks-centric one.

Then they push again

We're on Databricks but half our reads come from Trino. Now?

That pushes me toward Iceberg, or at least toward checking whether Delta's Trino support covers our actual read patterns at acceptable performance — including whether the features we rely on, like deletion vectors or liquid clustering, degrade or fail outside Databricks. The failure mode I'd be guarding against is a format that's excellent on one engine and second-class on the other, because the Trino half of the org then quietly builds copies of everything to work around it, and now we have a consistency problem instead of a format problem. I'd validate with a benchmark on our real tables rather than trusting a feature matrix.

03
Your predicate pushdown isn't working. The filter is on a column that definitely exists. Why?
Three plausible causes; a strong answer names more than one.
What a strong answer covers

Most likely the data isn't ordered by that column, so every row group's min/max spans nearly the full value range and no row group can be excluded. Statistics only enable skipping when values are clustered. Fix by sorting or Z-ordering on write.

Other real causes worth checking:

  • The predicate isn't pushable. Wrapping the column in a function — WHERE date(ts) = '2026-08-09', WHERE upper(country) = 'IN' — usually blocks pushdown because statistics are on the raw column. Rewrite as a range on the raw column.
  • Type mismatch or implicit cast between the literal and the column type.
  • Statistics missing. Some writers don't emit stats for all types, and very wide string columns often have stats truncated or disabled.
  • The filter is applied after a join or aggregation in the plan, so it never reaches the scan — check the physical plan for where the filter actually sits.
Then they push again

How would you verify which one it is, rather than guessing?

Read the physical plan first — it shows PushedFilters on the scan node, so I can immediately see whether the predicate reached the reader at all. That splits the problem in half: if it isn't pushed, it's a rewrite or type problem; if it is pushed but nothing is skipped, it's a data-layout problem. For the second case I'd compare files scanned against files in the partition — Iceberg and Delta both expose this — and inspect the per-file statistics directly to see whether the min/max ranges overlap. Overlapping ranges across every file is the definitive fingerprint of unsorted data.

04
Why do we even keep raw events after building the aggregates? It's ninety percent of our storage cost.
Cost questions test whether you can argue for the expensive option on the merits.
What a strong answer covers

Because aggregates encode the questions we already knew to ask, and the raw log is what lets us answer new ones. Concretely: a new attribution window, a re-computation after a bug in the aggregation logic, a backfill of a feature that didn't exist when the event was written, an audit or advertiser dispute, and any ML training set that needs event-level granularity — none of those are recoverable from rollups.

That said, I wouldn't defend keeping everything forever at the same tier. I'd propose a lifecycle: hot recent data in the query-optimised format, older data moved to cheaper storage classes, and a genuine retention policy driven by the longest window anyone actually reprocesses plus regulatory requirements. Also worth checking whether the raw table is as compact as it could be — column pruning, better encoding, and compaction often reclaim a large fraction without losing anything.

Then they push again

Legal says we must delete a user's events on request. How does that work on an append-only log in object storage?

This is exactly what row-level deletes in a table format are for — a merge-on-read delete file marks the rows, and compaction eventually rewrites the affected data files to physically remove them. The important detail is that the delete isn't real until compaction runs, so the retention job and the deletion SLA have to be coordinated, and old snapshots must be expired or the data is still reachable via time travel.

The architecturally cleaner approach is crypto-shredding: store the user identifier encrypted with a per-user key, and delete the key. The rows remain but become unreadable, which satisfies deletion for most regimes without rewriting petabytes. It's worth naming both and noting that which one is acceptable is a legal question, not an engineering one.

05
Give me a schema for storing thirty days of impressions such that reach and frequency by campaign returns in under two seconds.
They want layers, not one table.
What a strong answer covers

No single table serves both, so I'd design three layers.

Raw: Iceberg table, partitioned by event_date (hour if volume demands), sorted by campaign_id then device_id. Columns include event_id, event_time, ingest_time, campaign_id, device_id, creative_id, plus context. This is the source of truth and is never queried by the API.

Daily sketch table: one row per (campaign_id, event_date) holding an impression count and a serialised HyperLogLog sketch of device IDs. This is small — hundreds of thousands of rows for 30 days — and it is the key design choice, because sketches merge. Reach for any date range is the union of the sketches; a stored distinct count would not be summable.

Serving: that table in a low-latency store keyed by campaign, or cached. A 30-day query merges 30 sketches, which is microseconds of work.

Frequency distribution needs slightly more: either per-frequency-bucket sketches, or a device-level daily impression count table rolled up for exact small-N frequency.

Then they push again

The advertiser says the reach number is wrong — it doesn't match their own count. What do you tell them?

First, separate the two possible causes rather than defending the number. HyperLogLog is approximate, with error around 1–2% at standard precision, so a small discrepancy is expected and I'd state the error bound up front rather than let it be discovered. But a large discrepancy is not an approximation problem, and I'd go looking for a definitional mismatch: are we counting the same identifier (device vs. household vs. logged-in user)? The same time zone and day boundary? Are we deduplicating differently? Do they include an impression we filter as invalid traffic?

In my experience the answer is almost always definitional, not numerical. This is why an agreed metric definition in a semantic layer matters more than the sketch precision — and if we truly need exactness for billing, that's a different pipeline with exact distinct counts, accepting the cost.

Say it in sixty seconds
  1. Parquet stores columns in chunks within row groups, with min/max stats in the footer — that's what enables projection and predicate pushdown.
  2. Pushdown only skips data if the table is sorted or clustered on the filter column.
  3. Table formats (Iceberg/Delta/Hudi) add ACID commits, time travel, schema evolution, and row-level deletes over object storage.
  4. Partition on the near-universal filter (time) at hundreds-of-MB granularity; cluster on secondary filters. Never partition on a high-cardinality ID.
  5. Keep event_time and ingest_time separately — late data is the gap between them.
  6. Point-in-time correctness needs as-of joins against versioned features, or you leak the future into training.
What a weak answer sounds like
  • Treating Parquet as "a compressed file format" with no mention of row groups or statistics.
  • Proposing partitioning by user or device ID.
  • Describing a table format only as "it gives you ACID" with no mechanism.
  • Designing one table to serve both raw analysis and a two-second API.
  • Not distinguishing event time from processing time anywhere in the design.

Spark, deeper

Memory, executors, and the knobs that matter

Stage 02 covered why a job shuffles. This is why it dies. Executor memory, caching, serialisation, and UDF cost are where CTV-scale jobs actually fail, and where an interviewer can tell in one answer whether you have operated a cluster.

The executor memory model

Know this diagram in words — almost every OOM question resolves into it.

Each executor's JVM heap is split by spark.memory.fraction (default 0.6) into a unified region and the rest, which is user memory for your own data structures. The unified region is further split by spark.memory.storageFraction (default 0.5) into:

  • Execution memory — shuffle buffers, joins, sorts, aggregations. Spills to disk when exhausted.
  • Storage memory — cached RDD/DataFrame blocks and broadcast variables. Evicts blocks when exhausted.

The two borrow from each other: execution can evict cached blocks to reclaim space, but storage cannot evict execution. This asymmetry is the practical point — aggressive caching does not protect your cache, and it does starve execution until it doesn't.

Outside the heap sits overhead memory (spark.executor.memoryOverhead), covering JVM internals, off-heap buffers, and — critically for you — the Python worker processes in PySpark. A PySpark job with heavy UDFs can be killed by the resource manager for exceeding container limits while the JVM heap looks fine. That is the single most confusing OOM in PySpark and worth naming unprompted.

Reading the error

java.lang.OutOfMemoryError: Java heap space → heap too small for the partition. Container killed by YARN for exceeding memory limits → overhead exhausted, often Python. ExecutorLostFailure after long GC → memory pressure, not necessarily exhaustion.

Sizing executors

The classic anti-patterns are one giant executor per node (GC pauses become unmanageable, and HDFS/object-store throughput per JVM plateaus) and one core per executor (no memory sharing, broadcast copied per executor, scheduling overhead).

Conventional starting point: 4–5 cores per executor, memory sized so that heap / cores comfortably exceeds your largest expected per-task working set, plus 10–15% overhead (more for PySpark). Leave a core and a gigabyte or two per node for the OS and node manager.

Dynamic allocation scales executors with pending tasks. Useful for spiky and shared clusters; it interacts badly with caching (an idle executor holding your cache may be reclaimed) so pair it with an external shuffle service, and be aware that on cloud spot instances the combination of dynamic allocation and preemption causes shuffle-file loss and stage recomputation.

Speculative execution relaunches straggler tasks on other executors and takes whichever finishes. It rescues jobs from a slow node — and it actively wastes resources on skew, because the duplicate task is slow for the same reason. Do not offer speculation as a skew fix.

Caching: when it helps and when it hurts

Cache when a DataFrame is reused across multiple actions and recomputation is expensive. That's the whole rule, and it is narrower than people apply it.

LevelBehaviourUse
MEMORY_ONLYRecompute on evictionCheap-to-recompute data
MEMORY_AND_DISKSpill to disk on evictionDefault sensible choice
MEMORY_AND_DISK_SERSerialised — smaller, more CPUMemory-constrained
DISK_ONLYNo heap useVery expensive recompute, large data

Why caching hurts: cached blocks occupy storage memory that execution then has to evict anyway; caching a DataFrame used once is pure overhead; and caching before a filter caches rows you're about to discard. A frequent real bug is caching a wide table then selecting three columns — cache the projected version instead.

Always unpersist() when done, especially in long-running or iterative jobs. And know that cache() is lazy — nothing is cached until an action runs.

Checkpointing is different and often the better tool for long lineages: it writes to reliable storage and truncates lineage, so failure recovery doesn't replay the whole DAG. In iterative algorithms — identity-graph label propagation, for instance — lineage grows each iteration and periodic checkpointing is what keeps recovery tractable.

Serialisation, codegen, and the cost of Python

The DataFrame API runs through Tungsten: off-heap binary row format, cache-aware layout, and whole-stage code generation that fuses several operators into one generated Java method. That's why DataFrame operations vastly outperform equivalent RDD code — and why anything that breaks out of codegen is expensive.

Python UDFs break out of it completely. Each row is serialised from the JVM to a Python process, evaluated, and serialised back. You lose codegen, you lose the columnar format, and you add per-row IPC. On a large impression table this is routinely the dominant cost in a job.

The ladder, best to worst:

  1. Built-in functions. Fully optimised, pushed into codegen. Most parsing, date arithmetic, string manipulation, and JSON extraction already exists as a built-in.
  2. Pandas / Arrow UDFs. Batch rows via Arrow, amortising serialisation over a vector. Often 10× a plain Python UDF and a legitimate answer when you need custom logic.
  3. Scala/Java UDF. Stays in the JVM. Better than Python, still blocks some optimisation.
  4. Plain Python UDF. Last resort.

For RDD-level work, Kryo serialisation is meaningfully faster and more compact than Java serialisation and requires registering your classes to get the full benefit.

Reading the Spark UI like an operator

Rehearse a tour of this — being specific about where you look is a strong signal.

  • Jobs tab: which job is slow, and whether stages are running or queued. Long gaps between stages point at driver-side work — file listing, plan generation, collecting to driver.
  • Stages tab → the summary metrics table. This is the most useful screen in Spark. It shows min / 25th / median / 75th / max for task duration, shuffle read, spill, and GC. A max far above the median is skew, immediately and quantitatively.
  • Spill (memory) and spill (disk) columns: non-zero means partitions exceed execution memory. Raise partition count or executor memory.
  • GC time as a fraction of task time: above roughly 10% is a memory-pressure signal.
  • SQL tab: the actual physical plan with row counts and time per operator, plus whether AQE re-planned. This is where you confirm a broadcast happened or a filter was pushed down.
  • Storage tab: what is actually cached and what fraction is resident. Frequently reveals a cache you thought was helping is only 30% in memory.
  • Executors tab: per-executor task counts, failures, and memory. Uneven task counts point at locality or preemption.
The configs worth knowing by name

spark.sql.shuffle.partitions, spark.sql.adaptive.enabled, spark.sql.autoBroadcastJoinThreshold, spark.sql.files.maxPartitionBytes, spark.executor.memoryOverhead, spark.sql.adaptive.skewJoin.enabled. Don't recite them unprompted — but naming the right one at the right moment is credible.

Pushback

Now defend it

Each of these is a real interrupt. Commit to an answer before you reveal — reading the model answer without having tried is how you end up recognising the material but not being able to produce it.

01
Your PySpark job dies with "Container killed by YARN for exceeding memory limits" but the heap looks fine. Explain.
This is the PySpark-specific one.
What a strong answer covers

Because the container limit covers more than the JVM heap. It includes overhead memory, and in PySpark the Python worker processes live there. If the job uses Python UDFs, or collects data into Python, or uses libraries that allocate outside the JVM, that memory grows independently of heap usage — so the heap can look healthy while the container breaches its limit and the resource manager kills it.

Immediate fix: raise spark.executor.memoryOverhead, typically to 15–25% of executor memory for Python-heavy jobs rather than the small default.

Better fix: reduce the Python footprint. Replace UDFs with built-in functions where possible, convert remaining ones to pandas/Arrow UDFs so data is batched rather than held per row, and check whether anything is being collected to the driver or into Python structures unnecessarily. Also reduce cores per executor — each core runs its own Python worker, so eight cores means eight Python processes sharing that overhead allocation.

Then they push again

You raised overhead to 8GB and it still dies, intermittently, on about one task in a thousand.

Intermittent and rare points at data, not configuration — a small number of pathological records rather than a general sizing problem. I'd stop raising memory and go find them.

Likely candidates in a CTV context: a bid request row with an enormous JSON payload or a deeply nested array of deals; a device with a pathological number of events landing in one group; a corrupt record that expands hugely on parse. Any of these can make one task's working set orders of magnitude larger than the median while every other task is fine.

To locate it I'd look at the task-level metrics for the failing stage and find which partition it is, then inspect the keys in that partition — or add a cheap instrumentation pass computing the max serialised size per row or per group. Once identified, the fix is usually a guard: cap or truncate outsized payloads, route them to a quarantine path, and alert — rather than sizing the entire cluster for the worst row in a billion.

02
A colleague cached every intermediate DataFrame "to be safe." What do you tell them?
Be specific about the mechanism, not just "don't".
What a strong answer covers

That it's likely making the job slower, and I'd explain the mechanism rather than assert it.

Cached blocks occupy storage memory inside the unified region. Execution memory can evict them, but every eviction wastes the work of caching, and until eviction happens the cache is squeezing the memory available for shuffles, joins, and sorts — which is what pushes tasks into spilling. So the cache doesn't merely fail to help; it actively causes disk I/O elsewhere.

Caching only pays when a DataFrame is consumed by multiple actions and recomputation is genuinely expensive. A DataFrame used once should never be cached. A DataFrame cached before a filter or projection should be cached after them instead.

I'd point them at the Storage tab to see the actual resident fraction — usually a chunk of what they cached isn't fully in memory anyway, so they're paying the cost and getting partial benefit. And I'd suggest checkpointing instead where the real concern is a long lineage rather than reuse.

Then they push again

They say caching protects against recomputation if an executor is lost. Aren't they right?

Partly, and it's a fair point worth conceding rather than steamrolling — but caching is the wrong instrument for it. Cached blocks live in executor memory, so losing the executor loses the cache too. It protects against recomputation from other failures, not from the executor loss they're worried about, unless replication is enabled, which doubles the memory cost.

What actually addresses that concern is checkpointing: writing to reliable storage and truncating lineage, so a lost executor triggers a re-read rather than a replay of the whole DAG. It costs a write, but it's durable in a way that cache isn't.

So I'd frame it as: they've identified a real risk and picked a mechanism that doesn't cover it. In a long pipeline with an expensive wide stage in the middle, a single checkpoint after that stage gives them the protection they want at a fraction of the memory pressure they're currently creating.

03
You need to parse the VAST XML stored in a string column across 50 billion rows. How?
CTV-flavoured UDF question. Avoidance first.
What a strong answer covers

First I'd try hard not to parse XML at that scale at all. Fifty billion parses of a complex document is enormous regardless of implementation, so my opening question is whether the fields we need can be extracted upstream — at ingestion, once, into typed columns — so downstream consumers read a column rather than re-parsing. If the VAST payload is only needed for a handful of fields, that's the right architecture and it converts a recurring cost into a one-time one.

If it must happen in Spark:

  • Reduce the volume first. Filter to the rows that need parsing before the parse, not after. Projection and predicate pushdown before an expensive operator is worth more than any tuning of the operator.
  • Use built-ins where the structure permits. If the needed values can be reached by regexp_extract or xpath functions, that stays in the JVM and in codegen.
  • Otherwise a pandas/Arrow UDF, batching rows so the parser is invoked over a vector and serialisation is amortised — not a per-row Python UDF, which would serialise 50 billion times.
  • Consider a Scala UDF if we have JVM capability, keeping everything in-process.

And I'd expect malformed documents at that volume, so the parse needs to fail soft into a quarantine column rather than kill tasks.

Then they push again

Parsing at ingest isn't possible — the requirement came later and we have three years of history to backfill.

Then I'd treat it as a one-time backfill designed as such, rather than as a query pattern. Concretely: run it once, write the extracted fields to a new typed table joined on the event key, and have all future consumers read that. The three-year cost is paid once instead of on every query, which is the important structural point.

For the backfill itself I'd partition the work by date and run it incrementally with checkpointing, so a failure resumes rather than restarts — three years in one job is a job that will fail somewhere and lose everything. I'd size it against a spot-instance cluster if the deadline allows, since the work is embarrassingly parallel and interruption-tolerant if partitions are idempotent.

I'd also validate the parse on a sample before committing the full run, because discovering the extraction logic is wrong after three years of compute is an expensive lesson. And I'd write the new table with the extraction logic version recorded, so if we find a bug we know exactly what needs redoing.

04
Walk me through diagnosing a job that's using 5% of cluster CPU and taking six hours.
Low utilisation is a different failure class from slow tasks.
What a strong answer covers

Low utilisation means we're not compute-bound, so the time is going somewhere other than doing work. I'd separate driver-side from executor-side first, using the Jobs tab timeline — long gaps between stages point at the driver, long stages with idle executors point elsewhere.

  • Driver bottleneck. File listing over millions of small files, plan generation on a huge query, or something being collected to the driver. Classic on a Hive-style table with hourly partitions and no compaction.
  • Insufficient parallelism. Too few partitions, so most cores are idle. A single non-splittable input file — gzip is the usual culprit — forces one task regardless of cluster size.
  • Skew. Near the end of a stage, one task runs while everything else has finished, so utilisation collapses. The summary metrics table shows this instantly.
  • External bottleneck. Reading from a rate-limited API or a database, or writing to a store that's throttling. CPU idle because we're waiting on I/O.
  • Scheduling. Dynamic allocation not granting executors, or queue contention on a shared cluster.

The Executors tab distinguishes several of these quickly: if half the executors have zero active tasks, it's parallelism or scheduling; if one has all of them, it's skew.

Then they push again

It's the small-files case — two million files a day from a streaming writer. Fix it.

Two fixes, and I'd do both because they address different halves.

Downstream: compaction. A scheduled job that rewrites each closed partition into files sized in the hundreds of megabytes. Straightforward, and it fixes every existing consumer immediately without changing the writer.

Upstream: reduce file production. Two million files a day usually means the streaming job triggers very frequently with high parallelism, and each micro-batch writes one file per partition per batch. Lengthening the trigger interval, or coalescing before write, cuts file count multiplicatively. There's a real trade-off with freshness that I'd want to negotiate rather than decide unilaterally — if the consumers need one-minute latency, we accept more files and lean harder on compaction.

Structurally: a table format helps a lot here, because query planning reads manifests rather than listing storage, so the driver-side listing cost largely disappears even before compaction runs. That doesn't remove the per-file read overhead, but it addresses the specific six-hour symptom, which was planning rather than reading.

Say it in sixty seconds
  1. Heap splits into unified (execution + storage) plus user memory; execution can evict storage, not vice versa.
  2. Overhead memory holds PySpark's Python workers — that's the OOM where the heap looks fine.
  3. 4–5 cores per executor; speculation rescues slow nodes and wastes resources on skew.
  4. Cache only for multi-action reuse, after filtering and projection; checkpoint to truncate long lineage.
  5. Built-ins > pandas/Arrow UDF > Scala UDF > Python UDF. Python UDFs break codegen and serialise per row.
  6. In the UI: stage summary metrics for skew, spill columns for memory, SQL tab for the plan, Storage tab for actual cache residency.
What a weak answer sounds like
  • Offering "increase executor memory" as the answer to every failure.
  • Not knowing why a PySpark container OOMs with a healthy heap.
  • Caching by default, or caching a DataFrame used once.
  • Suggesting speculative execution as a skew remedy.
  • Describing the Spark UI in general terms without naming a specific screen.

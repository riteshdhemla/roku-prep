Primer · before stage 03

Spark, from one machine to many

Stages 03–05 assume you can already picture a cluster running your code. This builds that picture from nothing, with small numbers you can hold in your head. No prior Spark needed — read it once and the vocabulary stops being vocabulary.

PrimerRead before 03–05No prior Spark needed

One machine, then many

You have a day of impressions — call it 1 TB — and a laptop with 16 GB of memory. You cannot load it. There are only two ways out, and Spark is the second one.

Read it in chunks on one machine. Works, but one CPU core does all the work, one chunk at a time.

Cut it into chunks and hand each to a different machine. Same chunks — but now hundreds of cores work at once. That is the whole idea. Everything else is detail about when the chunks have to talk to each other.

A chunk has a name: a partition. Its size is chosen so that one CPU core can hold it and work on it alone — in practice a few hundred MB. So 1 TB is not "one big job", it is roughly 5,000 independent small jobs.

The whole model in one sentence

Cut the data into independent chunks, do the same thing to every chunk in parallel, and move data between chunks only when the question forces you to. Everything expensive is that last part.

Five words, each of which is a physical thing

The vocabulary is small, and every word maps to something real. Keep this concrete cluster in your head: 20 executors, 4 cores each.

WordWhat it physically isIn our example
ClusterThe set of machines you rented20 machines
DriverOne process that holds the plan and hands out work. Does not process your data.1
ExecutorA process on a machine with its own memory, that actually processes data20
Core / slotOne thread inside an executor. Runs exactly one task at a time.20 × 4 = 80 slots
TaskThe work of applying your code to one partition5,000 tasks

Now the arithmetic that explains most tuning advice you will ever read. You have 5,000 tasks and 80 slots. Spark runs 80 at a time, so the stage takes about 63 waves. If each task takes 10 seconds, the stage takes around ten minutes.

Reason it through

Why is the default of 200 shuffle partitions wrong for almost every real job? Run the arithmetic in both directions.

Too few: with 200 partitions on 400 cores, half the cluster is idle no matter how much you pay. Worse, 1 TB across 200 partitions is 5 GB per task, which will not fit in the memory given to one core — so it spills to disk and the stage crawls.

Too many: at 500,000 partitions each task handles 2 MB, and the fixed per-task overhead — scheduling it, launching it, reporting it — starts to cost more than the work inside it.

So the target is a small multiple of core count: enough tasks that every core stays busy and a slow one can be absorbed, few enough that overhead stays invisible. Then check the second constraint separately: whatever the count, one partition must fit in one task's memory.

Nothing runs until you ask for an answer

This surprises everyone once. Read it as four lines that build a plan and one line that executes it.

LineWhat happens
df = spark.read.parquet(".../impressions")Nothing. Records the intent.
df = df.filter(col("dt") == "2026-08-09")Nothing.
df = df.groupBy("campaign_id").count()Nothing.
df.write.parquet(".../out")Everything.

Operations that describe a transformation are lazy; only an action — write, collect, count, show — triggers execution.

This is not laziness for its own sake. Because Spark sees the whole recipe before it starts, it can throw work away: read only the dt=2026-08-09 directory instead of the whole table, and read only the two columns you actually used instead of all 90. Neither optimisation is possible if it has to run each line as you type it.

Two consequences to expect:

Errors appear at the wrong line. A typo in the filter surfaces at the write, because that is when it ran.

Asking twice costs twice. Calling df.count() and then df.write(...) re-reads the source from scratch both times. Spark does not remember results unless you tell it to with cache().

The one question that decides everything: does this row need to meet another row?

You now have every idea you need to predict what a job will cost. Take any operation and ask that single question.

"No" — the chunk can answer alone. filter, select, withColumn: to decide whether a row survives a filter, you need that row and nothing else. Every partition is handled independently, in place, no data moves. These are called narrow operations, and they are nearly free — Spark even fuses a whole chain of them into one pass.

"Yes" — rows must be brought together. groupBy, join, distinct, orderBy: to count impressions per campaign, every row for campaign 42 must end up on the same machine. They start scattered across 5,000 partitions. So they have to move. These are wide operations, and that movement is the shuffle.

The sentence to keep

A shuffle is the price of making related rows meet. If you can answer the question without related rows meeting, it is cheap. If you cannot, it is expensive, and no amount of cluster is going to change that.

OperationDoes a row need to meet another?Shuffle?
filter, select, withColumnNoNo
unionNo — it just stacks partitions togetherNo
groupBy, aggYes — all rows of a keyYes
joinYes — matching keys from both sidesYes (unless one side is broadcast)
distinctYes — duplicates could be anywhereYes
orderByYes — a global order needs global comparisonYes

What the shuffle actually does, in four steps

When you can narrate this, most Spark questions answer themselves.

1. Partition. Each task takes its output rows and sorts them into buckets — one bucket per destination partition — by hashing the key. Campaign 42 always hashes to the same bucket number, so it always lands in the same place.

2. Write to local disk. Buckets are written to the executor's own disk, not sent directly. If the in-memory buffer fills first, it spills early. Spill is the single most common cause of a slow stage.

3. Wait. Nothing on the other side starts until every task has finished writing. This is a hard barrier.

4. Fetch and merge. Each destination task pulls its bucket from every source executor over the network, merges the streams, and only then runs your actual aggregation.

Reason it through

Both of the surprising parts follow from one fact: a task computing the total for campaign 42 cannot emit an answer until it is certain no more rows for campaign 42 are coming. Partial knowledge of a key is useless.

That forces the barrier — the receiver has to wait for every sender, so one slow task delays the entire stage, and adding machines does not help. It also forces materialisation: the sender cannot stream rows to a receiver that is not ready to consume them, so it parks them somewhere durable first, and local disk is the cheapest place. Which in turn explains the third surprise: if an executor dies after writing its buckets, that output is gone and those tasks must be re-run.

It also tells you the cost is not CPU. Memory access is ~100 ns; local SSD is ~100 µs; a network round trip is longer still. A shuffle is disk-bound and network-bound, which is why "the cluster is not busy but the job is slow" is such a common and confusing symptom.

One consequence worth knowing early: groupByKey ships every raw row across the network, while reduceByKey and the DataFrame agg functions add up what they can before sending, so only one partial result per key travels. Same answer, often an order of magnitude less traffic. The DataFrame API does this for you — which is precisely why a hand-written Python UDF that does its own aggregation is so often the reason a job is slow.

Three numbers tell you what is wrong

Open the Spark UI, click the slow stage, and look at the summary metrics table — it shows min, median and max across tasks. Almost every diagnosis is a comparison in that table.

What you seeWhat it meansFirst move
Max task time far above median — 199 tasks in 30s, one in 40 minutesSkew. One key has far more rows than the rest.Count the key distribution. Adding executors will not help — it is one task on one core.
Spill (memory / disk) non-zero across most tasksPartitions too big for the memory each task has.Raise the partition count; drop unused columns before the shuffle.
Large shuffle read, all tasks evenHonest volume. Nothing is broken; you are simply moving a lot.Move less: filter earlier, aggregate earlier, select fewer columns.

In adtech, skew is not an edge case — it is the default. A handful of campaigns and publishers carry a large share of traffic, and a null or sentinel device ID can be the single biggest "key" in the table.

Put it together

The pipeline ran in 12 minutes on Monday and 3 hours on Tuesday, with no code change. Reason it out in the order the model suggests.

Is it reading more? Check input size. Same. So it is not volume.

Is every task slow, or one task? Open the slow stage. 2,000 tasks finish in under a minute; one has been running for two hours. That single comparison eliminates almost everything — it is not cluster size, not memory settings, not the query shape.

One task means one key. Count the join key on a sample. device_id = '00000000-0000-0000' is 40% of Tuesday's rows: an upstream SDK started sending a placeholder.

Fix the cause. Those rows should not be joined at all — filter them. Not "add executors", which would have changed nothing, because 40% of the data was queued behind a single core.

The habit

Symptom → which number is abnormal → what physically produces that number → fix. Never symptom → fix. The middle two steps are the entire skill.

Check yourself

Answer out loud before revealing. Recognising an explanation is not the same as being able to produce one.

01
Your cluster has 400 cores and spark.sql.shuffle.partitions is left at its default. What goes wrong, and what would you set it to?
Two separate things go wrong. Naming only one is a half answer.
What a strong answer covers

The default is 200, so after any shuffle there are only 200 tasks for 400 cores. Half the cluster sits idle — you are paying for 400 cores and using 200.

Second, and usually worse: fewer partitions means each one is bigger. On 1 TB that is 5 GB per task, far more than the memory one core gets, so tasks spill to disk and the stage slows down for a reason that has nothing to do with idle cores.

I would set it to roughly 2–4× the core count — around 800–1,600 here — then check the Spark UI: each task should handle something in the low hundreds of MB with no spill. The extra factor over 1× matters because it lets a slow task be absorbed instead of leaving the whole cluster waiting on one straggler.

Then they push again

Why not set it to 100,000 and be safe?

Because per-task overhead is fixed — scheduling, launching, and reporting each task costs the same whether it processes 2 MB or 200 MB. At 100,000 partitions the useful work per task shrinks until the bookkeeping dominates, and the driver becomes a bottleneck tracking them all. There is a floor on useful partition size for the same reason there is a ceiling.

02
A colleague says df.count() is a good way to check their filter worked, then runs df.write(...). Why is that slower than they expect?
The answer is one word, but the explanation is the point.
What a strong answer covers

Laziness. df is not data, it is a recipe. count() is an action, so it executes the whole recipe — reading the source, applying the filter — to produce a number, then throws the rows away. write is another action, so it executes the entire recipe again from the source.

They paid for the read and the filter twice. If the plan contains a shuffle, they paid for that twice too.

The fix is df.cache() (or persist()) before the first action, which tells Spark to keep the computed rows in memory so the second action reuses them — worth it when a result is used more than once, and wasteful when it is not.

Then they push again

So should I just cache everything?

No — cached data occupies executor memory that execution would otherwise use, so over-caching causes the spilling you were trying to avoid. Cache a result that is genuinely reused, ideally after the expensive narrowing step (post-filter, post-aggregation) rather than the raw source. And for a long chain where the concern is recovery rather than reuse, checkpoint() is the different tool: it writes to reliable storage and truncates the lineage, so a lost executor does not replay the whole pipeline.

03
Which of these cause a shuffle, and why: filter, withColumn, union, distinct, orderBy?
Apply the one question to each. One of these catches people out.
What a strong answer covers

filter and withColumn: no. Each row is decided using only itself, so every partition proceeds independently.

union: no — this is the one people get wrong. Union just stacks the two sets of partitions together; no row needs to meet any other row, so nothing moves. (union also keeps duplicates, which is exactly why it is cheap.)

distinct: yes. A duplicate of a row in partition 1 could be sitting in partition 5,000, and the only way to know is to bring equal values together.

orderBy: yes. A global ordering requires globally comparing rows, so Spark range-partitions the data — sampling to find boundaries, then moving every row into the right range.

Then they push again

Then why is union followed by distinct often given as an anti-pattern?

Because the pairing hides the cost. union is free and distinct is a full shuffle, so writing a.union(b).distinct() reads as one cheap-looking line while the second half does all the work — and in SQL, UNION does exactly this implicitly, where UNION ALL would not. If you do not actually need deduplication, UNION ALL removes a shuffle for free. If you do need it, it is honest work — just know that is where the time went.

Say it in sixty seconds
  1. Data is cut into partitions; a task applies your code to one partition; tasks run on slots (executor cores), several waves deep.
  2. Nothing runs until an action. That is what lets Spark skip columns and directories — and why an error appears at the write.
  3. Ask of any operation: does a row need to meet another row? No → narrow, free. Yes → wide, shuffle.
  4. A shuffle is: bucket by hash → write to local disk → global barrier → all-to-all fetch → merge. Disk- and network-bound, not CPU-bound.
  5. Diagnose from the task distribution: max far above median is skew; spill everywhere is partitions too big; even and large is honest volume.
Signs the model has not landed yet
  • Saying Spark is fast "because it is in memory" — the interesting cost is disk and network at the shuffle.
  • Reaching for more executors before knowing whether one task or all tasks are slow.
  • Treating df as data rather than a recipe — the source of most surprise re-computation.
  • Mixing up in-memory partitions (units of parallelism) with on-disk partition directories (dt=.../hour=...).
  • Explaining a shuffle as an arrow on a diagram rather than as write-to-disk, wait, fetch, merge.

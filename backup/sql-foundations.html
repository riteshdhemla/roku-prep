SQL, in the order the engine runs it

Most SQL confusion comes from reading a query in the order it is written. The engine runs it in a different order, and once you can see that order the rules stop feeling arbitrary. Correctness first — grain, fan-out and NULLs — then speed.

PrimerRead before 06–08Correctness before speed

The order you write is not the order it runs

Nearly every "why won't SQL let me do this" question dissolves once you know this. You write a query top to bottom starting with SELECT. The engine evaluates it in a completely different order, and SELECT is close to last.

Read three familiar frustrations off that diagram:

"Why can't I use my alias in WHERE?" Because WHERE runs before SELECT, and the alias does not exist yet. ORDER BY runs after SELECT, which is why the same alias works there.

"Why can't I put SUM(revenue) > 100 in WHERE?" Because grouping has not happened yet — there is no sum to compare. That is what HAVING is for.

"Why is my LIMIT 10 still slow?" Because it is last. Everything before it — the join, the grouping, the sort — happened over the full data set to decide which ten rows win.

The distinction to keep

WHERE filters rows, before grouping. HAVING filters groups, after. If your condition mentions an aggregate it belongs in HAVING; if it does not, put it in WHERE — where it removes rows before the expensive part instead of after.

A join multiplies rows — it does not "add columns"

This one mental model prevents the most expensive class of quiet SQL bug: the query that runs fine, returns plausible numbers, and is wrong.

It is tempting to picture a join as gluing extra columns onto the side of your table. What actually happens is: for each row on the left, find every matching row on the right, and emit one output row per match.

So the row count changes based on how many matches there are:

Matches on the right per left rowResult
Exactly oneRow count unchanged — this is the case people assume
ZeroRow disappears (inner join) or is kept with NULLs (left join)
TwoRow is duplicated. Every measure on the left is now counted twice.
Ask this before every join

"How many rows on the right can match one row on the left?" If the answer is not "at most one", your aggregates will move. Check it directly: SELECT key, count(*) FROM right_table GROUP BY key HAVING count(*) > 1 LIMIT 5.

Real dimension tables break this constantly, and usually for a legitimate reason: a campaign table that is one row per campaign per day, or one row per campaign per version, is unique on (campaign_id, dt) but not on campaign_id alone. Joining on the partial key fans out. The fix is to join on the full key, or to deduplicate to the grain you actually want first.

Grain: what one row means

The single most useful habit in SQL is naming the grain of every table you touch — one sentence beginning "one row per...".

impressions: one row per impression. campaign_daily: one row per campaign per day. devices: one row per device.

Two operations change grain, and they are the two that cause trouble:

GROUP BY coarsens it deliberately. One row per impression becomes one row per campaign per day. That is the point of the query.

A join can change it accidentally. That is the fan-out above — the grain got finer without anyone asking.

Reason it through

Why does stating the grain catch bugs that reading the SQL does not? Because a wrong result and a right result look identical in the output — both are a table of plausible numbers. Grain gives you an independent prediction to check against.

If you say up front "this should be one row per campaign per day, so about 500 campaigns × 30 days ≈ 15,000 rows" and the query returns 31,000, you have found the fan-out before it reaches a dashboard. Without that prediction there is nothing to compare against, and the duplicate revenue ships.

It is the same discipline as sanity-checking units in physics: the arithmetic can be flawless and the answer still wrong, and the cheapest check is the one that does not involve redoing the arithmetic.

NULL is "unknown", not "empty"

NULL does not mean zero and it does not mean blank. It means the value is not known — and comparisons with an unknown produce unknown, which is not the same as false. SQL keeps only rows where a condition is definitely true.

That single rule generates all of the following:

ExpressionResultWhy
revenue = NULLNever trueIs an unknown equal to 10? Unknown. Use IS NULL.
COUNT(*) vs COUNT(col)DifferentCOUNT(*) counts rows; COUNT(col) skips NULLs.
SUM(x) over zero rowsNULL, not 0No rows means no known total. Wrap in COALESCE(..., 0) if you want a zero.
x NOT IN (1, 2, NULL)Never returns anythingSee below — the classic trap.

The NOT IN trap is worth walking through, because it silently returns an empty result rather than an error. x NOT IN (1, 2, NULL) expands to x <> 1 AND x <> 2 AND x <> NULL. For x = 3 that is true AND true AND unknown, which is unknown — not true — so the row is dropped. Every row is dropped, for any x. If the subquery inside a NOT IN can produce even one NULL, the whole query returns nothing.

Use NOT EXISTS instead, which is null-safe and usually plans better as an anti-join.

LEFT JOIN then WHERE quietly becomes INNER JOIN

This follows from the two previous sections, and it is worth its own heading because it is so common.

You want every impression, with click information where a click exists:

QueryWhat you get
FROM impressions i LEFT JOIN clicks c ON c.imp_id = i.id
WHERE c.ts > '2026-08-09'		Only impressions that were clicked. The left join did keep unclicked rows, filling c.ts with NULL — then WHERE compared NULL to a date, got unknown, and dropped them.
FROM impressions i LEFT JOIN clicks c ON c.imp_id = i.id AND c.ts > '2026-08-09'Every impression, with click data attached only when it matches. The condition is part of what counts as a match, not a filter applied afterwards.
The rule

A condition on the right-hand table of a LEFT JOIN belongs in ON. A condition on the left-hand table belongs in WHERE. Putting a right-side condition in WHERE throws away the outer-ness you asked for.

Window functions: aggregate without collapsing

The difference from GROUP BY is exactly one thing: row count.

GROUP BY campaign_id takes 1,000 rows and gives you 5 — the detail is gone. SUM(...) OVER (PARTITION BY campaign_id) takes 1,000 rows and gives you 1,000, each one still itself but now carrying its campaign's total alongside. That is what lets you compute "this impression's revenue as a share of its campaign" in one pass.

Three parts, and only the first is required:

PARTITION BY — which rows count as "the group" for this row. Leave it out and the group is the whole result set.

ORDER BY — the order within the group. Required for anything positional: ROW_NUMBER, LAG, running totals.

The frame — which rows within the group are included, defaulting to everything from the start of the partition up to the current row when you supply an ORDER BY. This default surprises people: with ORDER BY, SUM becomes a running total rather than the group total.

The most common practical use is deduplication — keep the latest row per key:

GoalPattern
Latest row per deviceROW_NUMBER() OVER (PARTITION BY device_id ORDER BY ts DESC) then keep = 1
Compare a row to the previous oneLAG(value) OVER (PARTITION BY k ORDER BY ts) — not a self-join
Share of group totalvalue / SUM(value) OVER (PARTITION BY k)

That middle row matters for performance as well as clarity: comparing each row to its neighbour with a self-join is a quadratic shuffle, while LAG is one pass over sorted partitions.

Then, and only then, make it fast

Correctness first — grain, fan-out, NULLs. Once the answer is right, the performance model is short enough to state in one line, and stage 08 unpacks it:

Read less → shuffle less → shuffle better

Scan fewer partitions and fewer columns; move fewer rows across the network by filtering and aggregating before joining; only then worry about join strategy. Tuning a join on a query that scans the whole table is decorating.

The one habit worth adopting now: aggregate before you join whenever the semantics allow. Joining a billion-row fact table to something you were about to group anyway moves a billion rows so you can throw most of them away. Grouping first moves thousands.

Check yourself

Answer out loud before revealing. Recognising an explanation is not the same as being able to produce one.

01
You add a join to a campaign dimension table to pick up the campaign name. Total revenue goes from $2M to $3.1M. Nothing else changed. What happened?
The join did exactly what joins do.
What a strong answer covers

Fan-out. The dimension table is not unique on campaign_id, so some impressions matched more than one row and were duplicated — and their revenue was counted once per duplicate.

I would confirm it in one query: SELECT campaign_id, count(*) FROM campaigns GROUP BY 1 HAVING count(*) > 1. The fact that revenue grew by roughly 55% rather than doubling tells me only some campaigns are affected, which fits a table that is one row per campaign per version or per day.

The fix depends on what the extra rows mean. If the table is versioned, join on the full key — including the effective date — or select the current version first. If they are genuine accidental duplicates, deduplicate to one row per campaign before joining. What I would not do is wrap the result in SELECT DISTINCT, which hides the fan-out and breaks as soon as two real rows are legitimately identical.

Then they push again

The dimension is small. Could you avoid the join entirely?

Often, yes — and it sidesteps the whole class of bug. If all you need is a label for display, attach it at the very end, after aggregating to one row per campaign: the join then happens against thousands of rows instead of a billion, so a fan-out would be obvious immediately and the cost is negligible. More generally, joining a dimension before aggregating is both the riskier and the more expensive order. Aggregate to your target grain first, then decorate.

02
Why is WHERE date(event_ts) = '2026-08-09' slow on a table partitioned by dt, when WHERE dt = '2026-08-09' is fast?
Think about what the engine must know before it reads anything.
What a strong answer covers

Partition pruning happens before reading, by matching the predicate against directory names. dt = '2026-08-09' is a direct comparison on the partition column, so the engine reads one directory.

Once the column is wrapped in a function, the engine can no longer reason backwards from the result to which directories could produce it — so it does the only safe thing: reads every partition, computes date(event_ts) for every row, and then discards almost all of them. The work is the same shape, but the scan is thousands of times larger.

The fix is to leave the column bare and move the transformation to the literal side: a bounded range on the raw column, event_ts >= '2026-08-09' AND event_ts < '2026-08-10', or a direct predicate on the partition column.

Then they push again

Does this apply to non-partition columns too?

Yes, for the same reason at a smaller scale. Columnar formats keep min/max statistics per row group, and the reader skips a row group when the predicate cannot possibly be satisfied inside it. Wrapping the column in a function defeats that check as well, so you lose file-level skipping on top of partition pruning. It is also why an index in a transactional database goes unused the moment you compute on the indexed column — one rule, three places it shows up.

03
A query using WHERE device_id NOT IN (SELECT device_id FROM suppression_list) returns zero rows, but you can see qualifying rows in the table. What is going on?
It is not a data problem and not a permissions problem.
What a strong answer covers

The suppression list contains at least one NULL.

NOT IN expands to a chain of <> comparisons joined by AND. Comparing anything to NULL yields unknown, so the chain becomes true AND true AND unknown = unknown — and since SQL keeps only rows that are definitely true, every row is dropped. It returns nothing for any input, which is why it looks so much like a broken query rather than a logic error.

The fix is NOT EXISTS, which is null-safe because it asks whether a matching row was found rather than comparing values. WHERE NOT EXISTS (SELECT 1 FROM suppression_list s WHERE s.device_id = d.device_id). Adding WHERE device_id IS NOT NULL inside the subquery also works, but NOT EXISTS is the habit worth having — it does not depend on remembering the trap.

Then they push again

Why does the equivalent IN not have this problem?

Because a single true is enough. IN is a chain of ORs, so as soon as one comparison is true the result is true regardless of any unknowns beside it — the NULL is simply never decisive. With NOT IN the chain is ANDs, so every comparison must come back true, and one unknown poisons the whole expression. Same NULL, opposite outcome, purely because of how three-valued logic combines under AND versus OR.

Say it in sixty seconds
  1. It runs FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Aliases exist only from SELECT rightwards; WHERE filters rows, HAVING filters groups.
  2. A join multiplies rows. Before every join ask how many right-hand rows can match one left-hand row; if it is more than one, your totals move.
  3. State the grain — "one row per ..." — for every input and for your output. It is the cheapest bug-catcher there is.
  4. NULL is unknown, so comparisons return unknown, not false. Hence IS NULL, hence NOT EXISTS over NOT IN.
  5. A right-side condition in WHERE turns a LEFT JOIN into an inner join. Put it in ON.
  6. Window functions aggregate without collapsing rows — the tool for ranking, dedup, running totals, and neighbour comparisons.
Signs the model has not landed yet
  • Reading a query top to bottom and expecting it to execute that way.
  • Thinking of a join as "adding columns" rather than matching and multiplying rows.
  • Reaching for SELECT DISTINCT to fix a row count — it hides a fan-out instead of explaining it.
  • Treating NULL as zero or empty string, then being surprised by an empty result.
  • Optimising the SELECT list when the query is scanning the entire table.

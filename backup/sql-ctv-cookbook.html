The CTV query cookbook

These are the queries a CTV analytics panel actually asks for. Each one has a shape worth memorising, and each has a scale trap that turns a correct query into a four-hour job.

The delivery funnel

The first thing anyone asks of CTV logs: where does the opportunity go? Request → bid → win → impression → completion.

WITH req AS (
  SELECT request_id, publisher_id, device_id
  FROM bid_requests
  WHERE event_date = DATE '2026-08-09'
),
bid AS (
  SELECT DISTINCT request_id FROM bid_responses
  WHERE event_date = DATE '2026-08-09' AND bid_price IS NOT NULL
),
won AS (
  SELECT request_id, clearing_price FROM auctions
  WHERE event_date = DATE '2026-08-09' AND winner_id = 'us'
),
imp AS (
  SELECT DISTINCT request_id FROM impressions
  WHERE event_date = DATE '2026-08-09'
),
comp AS (
  SELECT DISTINCT request_id FROM ad_events
  WHERE event_date = DATE '2026-08-09' AND event_type = 'complete'
)
SELECT r.publisher_id,
       COUNT(*)                                  AS requests,
       COUNT(b.request_id)                       AS bid,
       COUNT(w.request_id)                       AS won,
       COUNT(i.request_id)                       AS impressions,
       COUNT(c.request_id)                       AS completions,
       COUNT(w.request_id) * 1.0
         / NULLIF(COUNT(b.request_id), 0)        AS win_rate,
       COUNT(c.request_id) * 1.0
         / NULLIF(COUNT(i.request_id), 0)        AS completion_rate
FROM req r
LEFT JOIN bid  b USING (request_id)
LEFT JOIN won  w USING (request_id)
LEFT JOIN imp  i USING (request_id)
LEFT JOIN comp c USING (request_id)
GROUP BY r.publisher_id;
The traps

Every stage needs DISTINCT or a dedup, or a fan-out at one stage silently multiplies the counts downstream. NULLIF guards the division. And a chain of left joins off the largest table in the warehouse is the expensive part — at real volume, compute each stage as a pre-aggregated count by publisher and join five small results, rather than joining five large ones.

Reach, frequency, and the frequency distribution

Reach is distinct devices. Frequency is impressions over reach. The distribution is what people actually need, and it is a two-step aggregation.

WITH per_device AS (
  SELECT campaign_id, device_id, COUNT(*) AS imps
  FROM impressions
  WHERE event_date BETWEEN DATE '2026-08-01' AND DATE '2026-08-09'
    AND device_id IS NOT NULL
    AND device_id NOT IN (SELECT device_id FROM device_denylist)
  GROUP BY campaign_id, device_id
)
SELECT campaign_id,
       CASE WHEN imps = 1 THEN '1'
            WHEN imps = 2 THEN '2'
            WHEN imps = 3 THEN '3'
            WHEN imps BETWEEN 4 AND 5   THEN '4-5'
            WHEN imps BETWEEN 6 AND 10  THEN '6-10'
            ELSE '10+' END              AS freq_bucket,
       COUNT(*)                         AS devices,
       SUM(imps)                        AS impressions
FROM per_device
GROUP BY campaign_id, 2
ORDER BY campaign_id, MIN(imps);

Reach curve — cumulative reach by day, the thing planners want — needs first-exposure logic, because a device reached on day 1 must not be counted again on day 3:

WITH first_seen AS (
  SELECT campaign_id, device_id, MIN(event_date) AS first_date
  FROM impressions
  WHERE event_date BETWEEN DATE '2026-08-01' AND DATE '2026-08-09'
  GROUP BY campaign_id, device_id
)
SELECT campaign_id, first_date,
       COUNT(*) AS newly_reached,
       SUM(COUNT(*)) OVER (PARTITION BY campaign_id
                           ORDER BY first_date
                           ROWS UNBOUNDED PRECEDING) AS cumulative_reach
FROM first_seen
GROUP BY campaign_id, first_date;

Note the aggregate inside a window — SUM(COUNT(*)) OVER (...) — which is the compact idiom for a running total over grouped data and worth having ready.

Pods: position, separation, and per-break checks

Pod-aware queries are the CTV-specific thing a generic SQL candidate won't write.

Performance by pod position — comparing slot 1 to slot 5 is a routine ask:

SELECT pod_position,
       COUNT(*)                                        AS impressions,
       SUM(CASE WHEN completed THEN 1 ELSE 0 END)*1.0
         / COUNT(*)                                    AS completion_rate
FROM impressions
WHERE event_date = DATE '2026-08-09'
GROUP BY pod_position
ORDER BY pod_position;

Detecting a separation violation — the same advertiser twice in one break — is a self-join-free window problem:

SELECT session_id, break_id, advertiser_id, COUNT(*) AS slots
FROM impressions
WHERE event_date = DATE '2026-08-09'
GROUP BY session_id, break_id, advertiser_id
HAVING COUNT(*) > 1;

Pod fill rate requires knowing the slots offered, which lives on the request rather than the impression — so this is one of the few places a join back to the request side is unavoidable:

SELECT r.publisher_id,
       SUM(i.filled)     AS filled_slots,
       SUM(r.pod_slots)  AS offered_slots,
       SUM(i.filled) * 1.0 / NULLIF(SUM(r.pod_slots), 0) AS fill_rate
FROM (SELECT request_id, publisher_id, pod_slots
      FROM bid_requests WHERE event_date = DATE '2026-08-09') r
LEFT JOIN (SELECT request_id, COUNT(*) AS filled
           FROM impressions WHERE event_date = DATE '2026-08-09'
           GROUP BY request_id) i USING (request_id)
GROUP BY r.publisher_id;

Gaps and islands, and pacing

Gaps and islands is the pattern family behind sessionization, continuous-viewing detection, and delivery-outage detection. The trick is always the same: mark a boundary, then take a running sum of the boundary flag as a group ID.

Detecting hours where a campaign delivered nothing — a pacing alert query:

WITH hours AS (   -- a date spine; without it, missing hours are invisible
  SELECT campaign_id, h AS hour_ts
  FROM campaigns
  CROSS JOIN UNNEST(SEQUENCE(
      TIMESTAMP '2026-08-09 00:00:00',
      TIMESTAMP '2026-08-09 23:00:00',
      INTERVAL '1' HOUR)) AS t(h)
),
delivered AS (
  SELECT campaign_id, DATE_TRUNC('hour', event_time) AS hour_ts,
         COUNT(*) AS imps
  FROM impressions
  WHERE event_date = DATE '2026-08-09'
  GROUP BY 1, 2
)
SELECT h.campaign_id, h.hour_ts, COALESCE(d.imps, 0) AS imps
FROM hours h
LEFT JOIN delivered d USING (campaign_id, hour_ts)
WHERE COALESCE(d.imps, 0) = 0;
The date-spine point is worth volunteering

Aggregating a log tells you about hours that had events. A zero-delivery hour produces no row, so it cannot appear in the result. Generating the complete time grid and left-joining is the only way to see absences — and absence is exactly what a pacing or outage alert is looking for.

Pacing versus plan then follows naturally: cumulative delivery over the flight against the linear (or front-loaded) target.

SELECT campaign_id, event_date,
       SUM(imps) OVER (PARTITION BY campaign_id ORDER BY event_date
                       ROWS UNBOUNDED PRECEDING) AS delivered_to_date,
       goal_impressions
         * (DATE_DIFF('day', flight_start, event_date) + 1)
         / NULLIF(DATE_DIFF('day', flight_start, flight_end) + 1, 0)
                                                 AS target_to_date
FROM daily_delivery JOIN campaigns USING (campaign_id);

Nested payloads, top-N per group, and sampling

Bid requests are nested. Deals, impressions array, device object, extensions. Know the two operations:

-- explode an array of deals into rows
SELECT r.request_id, d.deal_id, d.bid_floor
FROM bid_requests r
CROSS JOIN UNNEST(r.deals) AS d;

-- reach into a struct / JSON blob
SELECT request_id,
       device.ifa                              AS device_id,
       device.geo.country                      AS country,
       JSON_EXTRACT_SCALAR(ext, '$.ssai.vendor') AS ssai_vendor
FROM bid_requests;

The trap: UNNEST multiplies rows. Any count after an unnest counts deal-rows, not requests. Aggregate back, or count DISTINCT request_id.

Top-N per group — top 5 creatives per campaign by completion rate:

SELECT * FROM (
  SELECT campaign_id, creative_id, completion_rate,
         ROW_NUMBER() OVER (PARTITION BY campaign_id
                            ORDER BY completion_rate DESC) AS rn
  FROM creative_daily
) WHERE rn <= 5;

Deterministic sampling — essential on bid requests, and it must be stable across reruns and joinable across tables:

WHERE ABS(FROM_BIG_ENDIAN_64(XXHASH64(CAST(device_id AS VARBINARY)))) % 100 = 0

Hash on the entity (device or request), never RAND(). A random sample changes on rerun, can't be joined to another sampled table, and breaks any per-device aggregation because you'd have partial histories.

Pushback

Now defend it

Each of these is a real interrupt. Commit to an answer before you reveal — reading the model answer without having tried is how you end up recognising the material but not being able to produce it.

01
Write me reach and average frequency for a campaign over its flight. Then I'll break it.
Anticipate the break: the naive answer double-counts or doesn't roll up.
What a strong answer covers
SELECT campaign_id,
       COUNT(*)                          AS impressions,
       APPROX_COUNT_DISTINCT(device_id)  AS reach,
       COUNT(*) * 1.0
         / NULLIF(APPROX_COUNT_DISTINCT(device_id), 0) AS avg_frequency
FROM impressions
WHERE campaign_id = :cid
  AND event_date BETWEEN :start AND :end
  AND device_id IS NOT NULL
GROUP BY campaign_id;

Points I'd make while writing it. The partition filter is first so we prune. Nulls are excluded explicitly, because a null device ID would otherwise either collapse into one phantom device or inflate the count depending on the engine. Approximate distinct is deliberate — exact COUNT(DISTINCT) shuffles every device ID.

And I'd flag the thing that will break: this cannot be computed from a daily aggregate table by summing. Daily reach doesn't add up to flight reach. If this needs to be fast, the daily table must store an HLL sketch rather than a count, and the query merges sketches.

I'd also note that average frequency is a weak statistic here — a mean of 3 is consistent with everyone seeing 3 or most seeing 1 and a few seeing 40 — so I'd normally return the distribution alongside it.

Then they push again

Now do it for the last 90 days, for all 40,000 active campaigns, refreshed hourly.

That changes it from a query problem to a pipeline problem, and I'd say so rather than try to make the query fast.

The batch pipeline maintains a daily table at (campaign_id, event_date) holding impressions and a serialised HLL sketch of device IDs. That's 40,000 × 90 ≈ 3.6 million rows — trivial. The hourly refresh only recomputes today's partition; closed days are immutable and never recomputed.

The query then merges 90 sketches per campaign, which is microseconds of work, and reach for any sub-range is free because sketches merge over any subset of days.

Two caveats I'd raise. Merging sketches gives correct union reach, but frequency distribution doesn't decompose that way — per-device counts across 90 days can't be reconstructed from daily sketches, so if the distribution is needed over the full range I'd keep a compact per-(campaign, device) running count table instead, or accept a sampled estimate. And the sketch error compounds slightly on merge, so I'd state the expected error at 90-day range rather than quote the single-day figure.

02
Find every household that saw the same creative more than twice in a single ad break.
The grain is the whole question.
What a strong answer covers
SELECT household_id, session_id, break_id, creative_id,
       COUNT(*) AS times_in_break
FROM impressions i
JOIN identity_map m ON i.device_id = m.device_id
WHERE i.event_date = DATE '2026-08-09'
GROUP BY household_id, session_id, break_id, creative_id
HAVING COUNT(*) > 2;

The reasoning I'd narrate: the grain of a violation is the break, so the group key is (session, break, creative) — grouping by day would answer a different question. Household rather than device requires the identity mapping, because two TVs in one home could each show the creative and that may or may not count as a violation depending on the product definition — which I'd ask about rather than assume.

Scale notes: this is a single grouped aggregation over one partition, no self-join, so it's cheap. The join to the identity map is the risk — that table is large, so I'd want it broadcast if it fits after projecting to two columns, or bucketed on device ID if this join is routine.

Then they push again

There's no break_id in the log. Only session_id and event_time.

Then breaks have to be inferred from timing, which is a gaps-and-islands problem — impressions within a session clustered tightly in time belong to the same break, and a gap of more than some threshold means content resumed.

WITH flagged AS (
  SELECT *, CASE WHEN event_time - LAG(event_time) OVER (
              PARTITION BY session_id ORDER BY event_time)
            > INTERVAL '2' MINUTE OR LAG(event_time) OVER (
              PARTITION BY session_id ORDER BY event_time) IS NULL
       THEN 1 ELSE 0 END AS new_break
  FROM impressions WHERE event_date = DATE '2026-08-09'
),
breaks AS (
  SELECT *, SUM(new_break) OVER (PARTITION BY session_id
              ORDER BY event_time ROWS UNBOUNDED PRECEDING) AS break_seq
  FROM flagged
)
SELECT session_id, break_seq, creative_id, COUNT(*) AS n
FROM breaks GROUP BY 1,2,3 HAVING COUNT(*) > 2;

I'd flag that the threshold is a guess and should be validated against the actual inter-impression gap distribution — pods are typically 60–120 seconds, so a 2-minute gap is plausible but the data should confirm it. And I'd say plainly that inferring break boundaries is a workaround: the durable fix is getting the pod identifier passed through from the ad server, because every downstream pod analysis will otherwise re-derive this heuristic slightly differently.

03
This query returns the right numbers on a sample and wrong numbers on the full table. It has three joins and a DISTINCT at the end. Diagnose.
The DISTINCT is the tell.
What a strong answer covers

The DISTINCT at the end is almost certainly hiding a fan-out, and on a sample the duplicates happened not to collide. Somewhere one of those joins is not on a unique key, so rows multiply, and the DISTINCT deduplicates the final row set while any aggregate computed before it — a SUM, a COUNT — has already been inflated.

How I'd confirm: check the row count after each join incrementally. If joining to the deals table triples the count, that's the culprit. Then check whether the join key is genuinely unique on the right side with a quick group-and-having.

Common CTV instances of this: joining to a deals or line-item table where a request matches several deals; joining impressions to ad_events where a single impression has four quartile rows; joining to a slowly-changing dimension without filtering to the version valid at event time, so one campaign matches three historical rows.

The fix is to make the join one-to-one before it happens — pre-aggregate the right side to the grain you need, or add the validity predicate — not to deduplicate afterwards.

Then they push again

The fan-out is from a type-2 dimension. Write the fix.

The join has to be constrained to the dimension version in effect at the event's timestamp, not merely matching on the key:

SELECT i.impression_id, i.event_time, c.campaign_name, c.advertiser_id
FROM impressions i
JOIN campaign_dim c
  ON i.campaign_id = c.campaign_id
 AND i.event_time >= c.valid_from
 AND i.event_time <  COALESCE(c.valid_to, TIMESTAMP '9999-12-31')
WHERE i.event_date = DATE '2026-08-09';

Two details that matter. COALESCE on the open-ended current row, because the live version typically has a null valid_to and a naive inequality would exclude it — silently dropping every event against currently-active campaigns, which is the worst kind of bug because the query still returns plausible results. And the half-open interval, >= paired with <, so an event exactly at a version boundary matches exactly one row rather than zero or two.

Performance-wise this is now an inequality join, so I'd want the equality on campaign_id doing the partitioning work and the dimension small enough to broadcast — which it usually is. And I'd add a uniqueness assertion on the dimension as a data-quality check, because overlapping validity ranges in a type-2 table produce exactly this fan-out and are invisible until someone counts.

Say it in sixty seconds
  1. Funnel: dedup each stage before joining, guard divisions with NULLIF, and pre-aggregate before joining at real volume.
  2. Reach needs first-exposure logic for curves; frequency needs a two-step aggregation, per-device then bucketed.
  3. Pod queries group on (session, break, position) — that's the CTV-specific grain.
  4. Generate a date spine and left-join, or zero-delivery hours are invisible.
  5. Gaps and islands: flag the boundary, running-sum the flag, group by the result.
  6. UNNEST multiplies rows; sample by hashing the entity, never RAND().
What a weak answer sounds like
  • Summing daily reach into period reach.
  • A trailing DISTINCT covering an unexamined fan-out.
  • Joining a type-2 dimension without a validity predicate.
  • Reporting average frequency with no distribution.
  • Using RAND() to sample a table that will be joined or rerun.

The eight problems, in their data-shaped form

These panels ask algorithm questions dressed as pipeline questions. The pattern is standard; the interesting half is the follow-up — "now it's ten billion rows across a cluster" — and that transition is what's being graded.

Both panelsLive codingPython

How these questions actually go

You will get a problem that looks like LeetCode, solve it, and then be asked to scale it. The single-machine solution is table stakes; the distributed follow-up is the interview. So for every pattern, prepare both halves and volunteer the second before being asked.

A reliable framing to use out loud:

  1. Clarify the input. Sorted or not? Fits in memory? Streaming or bounded? Can I make two passes?
  2. State the approach and complexity before writing.
  3. Write it. Handle the empty case and the single-element case.
  4. Volunteer the scale variant. "On one machine that's O(n log n); at ten billion rows I'd do this instead —"
The transition sentences worth memorising

"That's a hashmap on one machine; distributed, it's a shuffle on that key." / "Sorting in memory becomes a sort-merge, or I avoid it with a sketch." / "The seen-set doesn't fit, so it becomes a Bloom filter plus an exact check." / "Per-key state becomes a keyed aggregation with a watermark."

Dedup, top-k, and sliding windows

Dedup with a TTL

Single machine: a dict from key to timestamp, plus lazy expiry or a deque of insertion order. Distributed: a Bloom filter as the cheap negative test in front of an exact store, over a bounded window.

class TTLDedup:
    def __init__(self, ttl_s):
        self.ttl = ttl_s
        self.seen = {}          # key -> expiry
        self.order = deque()    # (expiry, key) for eviction

    def is_new(self, key, now):
        while self.order and self.order[0][0] <= now:
            _, k = self.order.popleft()
            if self.seen.get(k, 0) <= now:
                self.seen.pop(k, None)
        if key in self.seen:
            return False
        exp = now + self.ttl
        self.seen[key] = exp
        self.order.append((exp, key))
        return True

Scale answer: Bloom filter sized for expected cardinality in the window; on a hit, confirm against a key-value store; rotate two filters so the window slides without unbounded growth.

Top-k

Single machine: a min-heap of size k, O(n log k). Distributed: partial top-k per partition, then merge — correct because top-k is decomposable. Streaming with unbounded keys: Count-Min sketch plus a heap of candidates.

Sliding window aggregate

Single machine: a deque holding the window, with a monotonic deque for max/min in O(1) amortised. Distributed: a windowed keyed aggregation with a watermark, or DGIM for approximate counts over very long windows.

Sessionization, intervals, and graphs

Sessionization

Sort by (entity, time), then walk: if the gap since the previous event exceeds the threshold, start a new session.

def sessionize(events, gap_s):
    events.sort(key=lambda e: (e.device, e.ts))
    sessions, cur = [], None
    for e in events:
        if cur is None or e.device != cur['device'] \
           or e.ts - cur['end'] > gap_s:
            cur = {'device': e.device, 'start': e.ts, 'end': e.ts, 'n': 0}
            sessions.append(cur)
        cur['end'] = e.ts
        cur['n'] += 1
    return sessions

Scale answer: partition by device, sort within partition, apply the same walk — which is exactly the SQL LAG-plus-running-sum idiom. Watch for the hot-device skew.

Merge intervals

Sort by start, then extend or append. This is attribution-window overlap and viewing-time deduplication. Scale: partition by entity, since intervals only merge within an entity.

Union-find

The identity-graph answer. Path compression plus union by rank gives near-constant amortised time.

class DSU:
    def __init__(self):
        self.p, self.r = {}, {}
    def find(self, x):
        self.p.setdefault(x, x); self.r.setdefault(x, 0)
        while self.p[x] != x:
            self.p[x] = self.p[self.p[x]]   # path compression
            x = self.p[x]
        return x
    def union(self, a, b):
        ra, rb = self.find(a), self.find(b)
        if ra == rb: return False
        if self.r[ra] < self.r[rb]: ra, rb = rb, ra
        self.p[rb] = ra
        if self.r[ra] == self.r[rb]: self.r[ra] += 1
        return True

Scale answer: doesn't distribute directly — use iterative label propagation (min-label broadcast per round) or resolve within shards then reconcile across shards.

Sampling, streaming stats, and rate limiting

Reservoir sampling

A uniform sample of k from a stream of unknown length: keep the first k, then for the i-th item replace a random slot with probability k/i. Worth knowing because "sample the stream" is a plausible ask and the naive answer requires knowing n.

In practice at scale: prefer deterministic hash sampling — hash(key) % 100 == 0 — because it's stable across reruns, joinable across tables, and needs no coordination. Say this; it's the more senior answer.

Streaming quantiles

Exact requires storing everything. Use t-digest or a KLL sketch; both merge, so per-partition sketches combine.

Token bucket

class TokenBucket:
    def __init__(self, rate, capacity):
        self.rate, self.cap = rate, capacity
        self.tokens, self.last = capacity, time.monotonic()

    def allow(self, n=1):
        now = time.monotonic()
        self.tokens = min(self.cap,
                          self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= n:
            self.tokens -= n
            return True
        return False

Lazy refill on access rather than a background timer — that's the detail interviewers look for.

LRU cache

Dict plus doubly-linked list, or OrderedDict with move_to_end. The distributed version is a different problem entirely: consistent hashing across nodes, and the thundering-herd protection on a miss.

Concurrency in the coding round

If they ask for concurrent code, the expected shape is a bounded queue with worker threads and clean shutdown. The parts people miss are the parts that get graded.

def run_pool(items, work, n_workers=8, queue_size=100):
    q = Queue(maxsize=queue_size)       # bounded == backpressure
    results, errors = [], []
    lock = threading.Lock()

    def worker():
        while True:
            item = q.get()
            if item is SENTINEL:
                q.task_done(); return
            try:
                r = work(item)
                with lock: results.append(r)
            except Exception as e:       # never let a worker die silently
                with lock: errors.append((item, e))
            finally:
                q.task_done()

    threads = [threading.Thread(target=worker, daemon=True)
               for _ in range(n_workers)]
    for t in threads: t.start()
    for it in items: q.put(it)
    for _ in threads: q.put(SENTINEL)
    for t in threads: t.join()
    return results, errors

Four things being checked: the queue is bounded; shutdown is explicit via sentinels rather than a flag race; exceptions are captured rather than swallowed; and shared state is protected. Volunteer that for I/O-bound work this is right, and for CPU-bound pure Python it would need processes.

Pushback

Now defend it

Each of these is a real interrupt. Commit to an answer before you reveal — reading the model answer without having tried is how you end up recognising the material but not being able to produce it.

01
Deduplicate an impression stream. Ten billion events a day, duplicates arrive up to an hour apart.
State the memory budget before choosing a structure.
What a strong answer covers

First the sizing, because it determines everything: ten billion a day is roughly 400 million per hour, so a one-hour dedup window needs to track around 400 million keys. An exact hash set of 16-byte IDs plus overhead is tens of gigabytes — possible on one large machine, not comfortable, and not distributable as-is.

So: Bloom filter as the first gate, sized for 400 million elements at a chosen false-positive rate — at 1% that's around 500 MB, very manageable. A negative from the filter is definitive, so the vast majority of events (genuinely new) are admitted with no further work.

A positive is only probably a duplicate, so it goes to an exact check against a key-value store holding recent IDs with a TTL. That's ~1% of traffic plus the true duplicates, which is a tractable lookup rate.

Window handling: rotate two filters, each covering the window, swapping on a schedule so old entries age out — standard Bloom filters can't delete.

Distribution: partition by event_id hash so all copies of an ID land on the same worker, making each worker's filter independently correct. That's the key design point — without consistent partitioning, per-worker filters don't compose.

Then they push again

A false positive means we drop a real impression. That's revenue. Justify the 1%.

The 1% figure is the Bloom filter's false-positive rate, not the drop rate — and that distinction is the answer. A filter positive doesn't cause a drop; it triggers the exact check, which is authoritative. So a false positive costs one extra lookup, not a lost impression. The design has no false drops at all as long as the exact store retains the full window.

Where real risk lives is elsewhere, and I'd rather name that than defend a number. If the exact store's TTL is shorter than the actual duplicate delay, a genuine duplicate arrives after its record expired and gets admitted — that's a false negative, over-counting rather than under-counting. And if the exact store is unavailable, we have to choose a failure posture: admitting on error over-counts, rejecting on error drops revenue. For billing-grade data I'd admit and reconcile in batch, because over-counting is detectable and correctable downstream while a dropped impression is gone.

I'd also size the window from the measured delay distribution rather than the one-hour assumption in the question, and monitor the fraction of duplicates arriving near the window edge as an early warning that the window is too short.

02
Find the top 100 campaigns by impression count. The data is spread across 500 partitions.
Say why the decomposition is valid, not just what it is.
What a strong answer covers

Two phases. Each partition computes its local counts and emits its top 100 — a heap of size 100, O(n log 100) per partition. Then a single merge step combines 500 × 100 = 50,000 candidates and takes the global top 100.

The validity argument is the part worth stating: this works because a campaign in the global top 100 must appear in some partition's local top 100 only if counts are first fully aggregated per campaign within each partition. If a campaign's impressions are spread across all 500 partitions with a small count in each, it could be globally large and locally invisible.

So the correct decomposition is: shuffle by campaign_id first so each campaign's rows are co-located, aggregate to one count per campaign, then take local top-k and merge. Without the shuffle, the two-phase heap is wrong — and that's the trap in the question.

If a shuffle is too expensive, the alternative is a Count-Min sketch per partition, merged, giving approximate counts with a one-sided error — acceptable for heavy hitters, which top-100 by definition is.

Then they push again

Campaign counts are extremely skewed — the top campaign has 40% of all impressions. Does your plan still work?

The top-k logic still works, but the shuffle-then-aggregate step becomes the problem: 40% of ten billion rows land on one reducer task, which will spill and may fail.

The fix is two-phase aggregation, and it applies cleanly here because count is associative. Partial-aggregate within each partition first — map-side combine, which Spark's reduceByKey/DataFrame agg does automatically — so what crosses the network is one partial count per campaign per partition, not raw rows. The hot campaign then contributes 500 partial counts rather than four billion rows, and the skew disappears entirely.

That's worth stating as a general principle: skew on an associative aggregation is usually not a real problem, because pre-aggregation collapses it. Skew is a genuine problem on joins, where there's nothing to pre-aggregate, and on non-associative operations like median or exact distinct count. Being able to distinguish those two cases quickly is what stops you from salting things that didn't need it.

03
Write something that processes 10,000 URLs concurrently and returns results plus failures.
They're checking bounds, shutdown, and error capture.
What a strong answer covers

I'd use asyncio for I/O-bound work at this scale, with a semaphore bounding concurrency — firing 10,000 simultaneous requests exhausts file descriptors and hammers the target.

async def fetch_all(urls, concurrency=50, timeout=10):
    sem = asyncio.Semaphore(concurrency)
    results, errors = [], []

    async def one(session, url):
        async with sem:
            try:
                async with session.get(url, timeout=timeout) as r:
                    results.append((url, r.status, await r.text()))
            except Exception as e:
                errors.append((url, repr(e)))

    async with aiohttp.ClientSession() as session:
        await asyncio.gather(*(one(session, u) for u in urls))
    return results, errors

Points I'd narrate: the semaphore is the bound; gather with exceptions caught inside each task means one failure doesn't cancel the rest; a per-request timeout is non-optional or a hung connection holds a slot forever; and a single shared session reuses connections rather than opening 10,000.

I'd add that in production this needs retries with jittered backoff for transient failures, and a circuit breaker if the target starts failing broadly — retrying into a struggling service makes it worse.

Then they push again

Some of these URLs are slow but valid — 30 seconds. Your timeout kills them. How do you decide the timeout?

From the measured latency distribution rather than a guess, and I'd frame the trade-off explicitly. A timeout is a statement about how much of the tail you're willing to lose in exchange for bounding resource usage — setting it at the p99 loses 1% of valid responses and caps the worst case; setting it at 60 seconds keeps nearly everything but means a stalled endpoint holds a concurrency slot for a minute, and with a bounded semaphore that directly starves throughput for everything else.

The better answer is usually to stop treating all requests the same. Tiered timeouts by endpoint if we know some are legitimately slow; a short timeout with retry, since a retry that succeeds in two seconds beats one request waiting thirty; and separating slow known-valid endpoints into their own pool with its own concurrency budget so they can't starve the fast path.

I'd also want to know what happens downstream to a timed-out URL. If it's silently dropped, that's a data-loss bug wearing a timeout costume. It should land in the errors list and be retried or reported — which the code above does, and which is the reason to return failures explicitly rather than just logging them.

Say it in sixty seconds
  1. Solve it single-machine, state complexity, then volunteer the distributed variant unprompted.
  2. Hashmap → shuffle on the key. In-memory sort → sort-merge or a sketch. Seen-set → Bloom plus exact check.
  3. Dedup: Bloom gate over a rotating window, exact confirm, partitioned by the dedup key.
  4. Top-k distributes only after per-key aggregation; pre-aggregate to kill skew on associative operations.
  5. Prefer deterministic hash sampling to reservoir sampling — stable, joinable, no coordination.
  6. Concurrency answers get graded on bounds, explicit shutdown, captured exceptions, and timeouts.
What a weak answer sounds like
  • Solving the single-machine version and stopping.
  • Two-phase top-k without noticing the pre-aggregation requirement.
  • Unbounded queues, unbounded concurrency, or no timeout.
  • Swallowing exceptions in workers.
  • Reaching for multiprocessing on I/O-bound work.

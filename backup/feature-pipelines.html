End-to-end systems

From raw beacons to a served feature

Panel 2 asks explicitly for end-to-end pipelines supporting ML and Gen-AI, including feature generation and downstream consumption. This is where storage, Spark, streaming, and ML meet — and where training/serving skew is born.

The layered pipeline

Have one reference architecture you can draw in ninety seconds and then adapt.

  1. Ingest. Beacons and auction logs into Kafka; raw landing in object storage. Immutable, append-only, with event_time and ingest_time both preserved.
  2. Bronze → silver. Parse, validate, deduplicate, conform types, resolve identity. Output is a clean, typed impression table — the one everything downstream trusts.
  3. Gold / aggregates. Business-grain tables: daily campaign metrics with sketches, delivery state, segment membership.
  4. Feature generation. Offline features computed in batch over silver/gold; streaming features computed over the live stream. Both written to a feature store with the entity key and a feature timestamp.
  5. Training. Point-in-time joins against the feature store to build a training set; model artifact versioned alongside the feature set version.
  6. Serving. Online store for low-latency lookup; the model reads the same feature definitions.
  7. Monitoring. Data quality at each hop, drift on features, error on predictions once labels land.
The one-sentence version

"Raw immutable log, a cleaned conformed layer everyone shares, aggregates and features derived from it, offline and online paths built from the same definitions, and quality gates between each hop."

Training/serving skew and how it actually happens

Skew is when the feature value at training differs from the value at serving for the same logical feature. It doesn't show up offline, so it is discovered as an unexplained production gap.

The four mechanisms:

  • Two implementations. The offline feature is written in Spark SQL and the online one in the serving service's Java. They drift on an edge case — null handling, rounding, timezone — and nobody notices.
  • Different data. Offline features are computed over the settled table including late data; online features see only what has arrived. The offline version is systematically more complete.
  • Different timing. Offline joins the feature as of the label's day; online reads whatever the store holds at request time, which may be hours stale.
  • Backfill artifacts. A feature backfilled over history using logic that didn't exist then.

Mitigations, in order of strength: a single feature definition executed in both modes (the core promise of a feature store); logging features at serving time and training on those exact logged values, which sidesteps the problem entirely by making the served value the ground truth; and, failing both, an automated comparison job that samples entities and diffs offline against online values daily, alerting on divergence.

Point-in-time correctness, concretely

For each training row with a label at time t, every feature must be the value that was knowable strictly before t. The mechanics are an as-of join:

SELECT l.impression_id, l.label_time, l.completed,
       f.device_7d_impressions, f.device_completion_rate
FROM labels l
JOIN LATERAL (
  SELECT device_7d_impressions, device_completion_rate
  FROM device_features
  WHERE device_id = l.device_id
    AND feature_time <= l.label_time
  ORDER BY feature_time DESC
  LIMIT 1
) f ON TRUE;

Requirements this imposes upstream: feature tables must be versioned by time rather than overwritten, and the feature timestamp must reflect when the value became available, not when the underlying events happened. A feature computed from yesterday's data but only materialised at 6am today is not available for a 3am prediction — and encoding that correctly is what separates a correct pipeline from a subtly optimistic one.

Label timing is the mirror problem. A conversion label may land days after the impression, so a training set built too soon has false negatives — conversions that hadn't happened yet. Define an explicit label maturity window and exclude rows younger than it.

Backfills, reprocessing, and idempotency

Every pipeline gets rebuilt. Design for it rather than treating it as an incident.

  • Partition-parameterised jobs. The job takes the date as an argument, reads only that partition, and overwrites its output partition. Re-running produces identical output. No wall-clock dependence anywhere in the logic — CURRENT_DATE inside a transformation makes a job unbackfillable.
  • Versioned logic. Record which code version produced each partition, so when you fix a bug you know precisely what needs reprocessing.
  • Bounded blast radius. Backfill into a shadow table and swap, or use table-format snapshots so a bad backfill is one rollback rather than a restore from backup.
  • Ordering. Backfills must respect dependencies — regenerating features before the silver table they read is a classic way to produce confidently wrong data.
  • Throttling. A 3-year backfill launched at full parallelism will starve production jobs on a shared cluster. Chunk it and rate-limit.

Late data interacts with this directly: if a partition can still receive events for 48 hours, then "yesterday" isn't final. Either delay downstream consumption, or reprocess a trailing window every run and accept that recent numbers move.

Data quality as a gate, not a dashboard

A dashboard someone might look at is not a control. Quality checks should block promotion of a partition.

What to check, by hop: row counts against expected range; null rates on required fields; distribution shift on key columns; referential integrity (every impression has an auction); uniqueness on the supposed primary key; freshness (did the partition arrive at all); and business invariants (impressions ≤ auctions ≤ requests, spend ≤ budget).

Where they belong: after ingest, so bad data never enters silver; after feature generation, so a broken feature never reaches training or serving; and before model promotion.

What to do on failure: distinguish fail (block the partition, page someone) from warn (annotate and continue). Getting this wrong in either direction is costly — failing on soft checks trains people to ignore alerts, warning on hard checks lets corrupt data through.

The invariant worth stating

"A partition is not visible to consumers until it has passed its checks." That single property — publish-after-validate rather than validate-after-publish — prevents most downstream data incidents, and it's a design choice, not a tooling choice.

Pushback

Now defend it

Each of these is a real interrupt. Commit to an answer before you reveal — reading the model answer without having tried is how you end up recognising the material but not being able to produce it.

01
Design the feature pipeline for a model that predicts whether an impression will complete. Offline training, online serving at bid time.
The latency budget at bid time constrains everything.
What a strong answer covers

I'd start from the serving constraint, because it eliminates most designs: a bid response has single-digit milliseconds, so any feature requiring computation at request time is out. Everything must be a precomputed lookup.

Feature groups by entity and freshness:

  • Device/household — trailing 7-day impression count, historical completion rate, daypart pattern. Batch-computed daily, low churn, tolerant of staleness.
  • Creative — duration, historical completion rate by position, age. Batch daily.
  • Publisher/app/content — historical completion by pod position. Batch daily.
  • Request context — pod position, break duration, daypart, device type. Available in the bid request itself, no lookup at all.
  • Near-real-time — impressions to this device in the last hour, for frequency effects. Streaming, if the latency budget allows one more lookup.

Offline: Spark job over silver impressions writes feature rows keyed by entity with a feature timestamp, into the offline store. Online: the same rows pushed to a key-value store keyed by entity ID. Training: point-in-time join of labels to offline features.

Skew control: one definition executed both ways, plus logging the served feature vector with each prediction so we can train on exactly what serving saw.

Then they push again

You've got three lookups on the bid path — device, creative, publisher. That's your entire latency budget. Cut it.

A few options, and I'd want to know the measured per-lookup latency before choosing, since the answer differs if it's 1ms or 4ms.

Batch the lookups into one round trip — a multi-get against the same store, so we pay one network hop instead of three. Usually the easiest large win and it doesn't change the feature set.

Denormalise into a single key. Precompute a combined row keyed on the most selective entity, embedding the creative and publisher features. Costs storage and makes updates fan out, but reduces to one lookup.

Cache the low-cardinality features in process. Creative and publisher features change daily and there are relatively few of them — hold them in memory in the bidder, refreshed periodically. That eliminates two lookups entirely and leaves only the device lookup, which is genuinely high-cardinality.

That last one is where I'd start: it exploits the actual cardinality asymmetry rather than trading storage for latency. The trade-off to state is staleness — an in-process cache refreshed hourly means a new creative isn't scored correctly for up to an hour, so it needs a cold-start default and I'd want to check how often creatives launch mid-day.

02
Model performance dropped 15% in production last Tuesday. Walk me through the investigation.
Data before model. Almost always data.
What a strong answer covers

I'd work outward from the most common causes, and the first question is whether the model changed at all — if there was no deploy, it's data or environment, which narrows things immediately.

  1. Is it real? Check whether the metric drop is a measurement artifact — a labelling pipeline delay makes recent performance look bad because labels haven't landed. Very common and worth ruling out in five minutes.
  2. Input data. Compare feature distributions Tuesday versus the prior week. A feature that suddenly nulls out or shifts is the modal cause — an upstream schema change, a publisher integration change, a failed job leaving a partition partial.
  3. Feature freshness. Did the batch feature job run? A stale online store serving last week's device features produces exactly this.
  4. Skew. Compare logged serving features against offline recomputation for the same entities. Divergence points at an implementation split.
  5. Population shift. Did the traffic mix change — a large new publisher, a new device type, a campaign targeting an unusual segment? The model may be fine and simply operating outside its training distribution.
  6. The model itself. Only after the above: a deploy, a dependency version change, a feature-order mismatch in serialisation.

The segment breakdown usually localises it fastest — if the drop is entirely within one publisher, that's a very different investigation from a uniform decline.

Then they push again

Feature distributions are unchanged, no deploy, labels are complete. Now what?

Then the inputs and the model are both stable, so I'd look at what sits between them and at what the model's outputs are being used for.

Feature ordering or encoding. Distributions can be individually unchanged while the vector assembled at serving is wrong — a column reordering, a category-encoding map regenerated with different indices. This is invisible to per-feature distribution checks and is worth testing directly by scoring known inputs and comparing to expected outputs.

A feedback loop. If the model's decisions shape the data it sees, performance can degrade with no external change. A completion model that throttles low-scoring inventory stops observing those outcomes, retrains on a censored distribution, and drifts.

Something downstream changed how the score is used. A threshold adjustment, a bidding logic change, or another system's change that alters the population the model is applied to — the model is performing identically and the measured outcome moved.

Genuine concept drift — the relationship between features and outcome changed, perhaps a seasonal content shift or a new ad format. Same inputs, different meaning.

I'd test the ordering hypothesis first since it's cheap and mechanical, then look hard at whether anything consuming the score changed, because "no deploy" usually means no deploy to our service.

03
You need to backfill a new feature across three years. Go.
They want to hear idempotency, ordering, and blast radius.
What a strong answer covers

Before running anything: validate the logic on a sample — one week from an old period and one recent — and eyeball the distribution. Discovering the definition was wrong after three years of compute is expensive and avoidable.

Structure the job to take a date partition as a parameter, read only that partition's inputs, and overwrite its output. Re-runnable to identical output, so a failure resumes rather than restarts.

Check the inputs exist historically. A feature depending on a field added eighteen months ago cannot be computed before that, and the honest output is nulls with a documented start date — not a silently different definition for the early period, which would poison any model trained across the boundary.

Write to a shadow table and swap, or rely on snapshot rollback, so a bad backfill is reversible.

Chunk and throttle — run in date batches with bounded parallelism so it doesn't starve production jobs. Run oldest-first so partial progress is contiguous and usable.

Record the code version on each partition, and reconcile at the end: row counts and null rates per partition against expectations, so silent partial failures surface.

Then they push again

Halfway through, you realise the feature definition was subtly wrong. What's the damage and what do you do?

The damage depends entirely on whether anything has consumed it yet, so that's my first question, not my first fix.

If it's still in the shadow table and nothing reads it: cheap. Fix, re-run, no consumer ever saw it. This is the argument for shadow-write-then-swap in one sentence.

If it's been swapped in and a model has trained on it, the blast radius includes that model, and I'd want to know whether it's serving. Then: stop the backfill immediately rather than completing a run I know is wrong; determine the exact partition range affected using the recorded code version; and decide whether the model needs retraining or rollback based on whether the feature materially influenced it — a feature with low importance may not warrant a rollback.

The process lesson I'd draw, and state, is that the sample validation should have caught it and evidently wasn't thorough enough. The specific improvement is comparing the backfilled feature against an independently computed version on a sample, rather than just checking that the distribution looks plausible — plausible-looking wrong values are exactly the failure mode here. I'd want that as a standard step before any backfill, not just this one.

Say it in sixty seconds
  1. Raw immutable → cleaned silver → aggregates → features (offline + online from one definition) → training via point-in-time join → serving → monitoring.
  2. Skew arises from two implementations, different data completeness, different timing, or backfill artifacts.
  3. Log the served feature vector and train on it — the strongest skew defence available.
  4. Feature timestamp means availability time, not event time. Label maturity windows prevent false negatives.
  5. Backfill = partition-parameterised, overwrite-not-append, no wall-clock in logic, versioned, shadow-write, throttled.
  6. Quality checks gate publication: a partition isn't visible until it passes.
What a weak answer sounds like
  • One feature pipeline for training and a separately written one for serving, with no reconciliation.
  • No mention of point-in-time correctness.
  • Backfill jobs that append rather than overwrite.
  • Data quality as a dashboard rather than a gate.
  • Debugging a production drop by looking at the model first.

SQL, deeper

Reading the plan before blaming the warehouse

"Make this query faster" is the most common follow-up in a data panel. The answer is almost never a rewrite of the SELECT list — it's pruning, join order, cardinality, and what the engine could not push down.

Panel 2 coreDebuggingCost

How to read a plan

Read a physical plan bottom-up: leaves are scans, and data flows upward through joins and aggregations to the final projection. Four things to look for, in order:

  1. The scan nodes. How many partitions and files are being read, and what filters were pushed into the scan. If PushedFilters is empty or the partition count is the whole table, everything above it is irrelevant — fix this first.
  2. Exchange nodes. Each one is a shuffle. Count them. Two adjacent exchanges on the same key usually means a missed opportunity to reuse a partitioning.
  3. Join operators. BroadcastHashJoin vs SortMergeJoin, and which side is being broadcast. A broadcast on the wrong side is a classic silent problem.
  4. Row estimates versus actuals. If the optimiser thought a branch would produce 1,000 rows and it produced 800 million, every downstream decision was made on bad information — that's a statistics problem, not a query problem.

Most engines offer both a cost-based estimate (EXPLAIN) and post-execution actuals (EXPLAIN ANALYZE, or the Spark SQL tab). Always prefer actuals. The gap between estimate and actual is itself the most useful diagnostic.

The pruning checklist

Before anything clever, confirm the query is reading as little as possible. In order of impact:

  • Partition pruning. Is there a predicate on the partition column, and is it a form the engine can use? A literal or a bounded range works; wrapping the column in a function, comparing against a subquery result, or a non-deterministic expression often defeats it.
  • File / row-group skipping. Does the filter column correlate with sort order? If not, statistics don't exclude anything (stage 08). Check files-scanned versus files-in-partition.
  • Projection. Are you reading columns you don't use? On a wide bid-request table this is frequently the single biggest win, and SELECT * inside a CTE propagates it invisibly.
  • Predicate placement. Filters in a WHERE after a LEFT JOIN on the right-side table silently convert it to an inner join and may prevent pushdown. Put the predicate in the ON clause when you mean to preserve the outer semantics.
  • Early aggregation. Aggregating before a join, when semantics allow, shrinks the shuffle by orders of magnitude. This is the single most effective rewrite in adtech queries, where you routinely join a billion-row fact to something you're about to group anyway.
The order that matters

Read less → shuffle less → shuffle better. Almost every real optimisation lives in the first two. Tuning join strategy on a query that scans the whole table is decorating.

Join order, cardinality, and statistics

Cost-based optimisers choose join order from cardinality estimates, which come from table and column statistics. When statistics are stale or missing — very common on freshly written partitions — estimates collapse to defaults and the optimiser makes poor choices with total confidence.

Symptoms of a statistics problem: a plan that broadcasts something enormous, a join order that starts with the largest intermediate result, or estimated rows that differ from actuals by orders of magnitude. The fix is to compute statistics (ANALYZE TABLE) and, on Spark, rely on AQE to re-plan from runtime shuffle statistics, which is precisely the case AQE was built for.

Join order heuristic when you're doing it by hand: join to reduce cardinality as early as possible. Filter-then-join beats join-then-filter. Start from the most selective predicate.

Hints — BROADCAST, MERGE, SHUFFLE_HASH — exist and are a last resort. They freeze a decision that should adapt to data volume, and a hint that was right at 10 GB becomes an OOM at 100 GB. If you use one, it needs a comment explaining the data assumption and ideally a monitor on that assumption.

On the last one — CTE materialisation semantics vary by engine, and knowing that they vary is the right answer. Some inline every reference, some materialise once. If a CTE is expensive and referenced three times, don't assume.

When the query isn't the problem

Keep a short list of causes that live outside the SQL, because interviewers like the candidate who checks these.

  • Small files. Planning time dominated by listing; the query itself is fine.
  • Concurrency. The warehouse is queued behind other work; the same query is fast at 3am.
  • Cold cache. First run reads from object storage, second is warm. Benchmark both and say which you're quoting.
  • Result size. A query returning 10 million rows to a BI tool is slow at the client, not the engine.
  • The wrong table. The most common real fix: someone is querying raw impressions for something the aggregate table already answers. The query is optimal and the architecture is wrong.

Cost is the other half of the answer. Most warehouses bill on bytes scanned or compute-seconds, so reading less is simultaneously the performance fix and the cost fix — a useful thing to say out loud, since it aligns the engineering argument with the finance one.

Pushback

Now defend it

Each of these is a real interrupt. Commit to an answer before you reveal — reading the model answer without having tried is how you end up recognising the material but not being able to produce it.

01
A dashboard query takes 90 seconds. Make it fast. You can ask me three questions first.
The questions are the answer — pick ones that partition the problem.
What a strong answer covers

My three would be:

  1. What does the plan say about bytes and partitions scanned? This immediately separates a pruning problem from a shuffle problem, and pruning is both more common and more fixable.
  2. Is it querying raw event tables or an aggregate? If a dashboard is hitting raw impressions, the fix is architectural, not a rewrite.
  3. How fresh does it need to be? This determines whether a materialised aggregate is even permissible, and it's the constraint that decides between three different solutions.

With those answered, the ladder is: prune first (partition predicate, projection, file skipping); then reduce the shuffle (pre-aggregate before joining, fix join strategy); then move the work offline (materialise a daily aggregate, refresh incrementally); and only then consider caching, which I'd treat as a last resort because it hides rather than fixes.

My prior for a 90-second dashboard query is that it's reading raw data that a pre-aggregate should already summarise — that's the modal cause and it's worth stating as a hypothesis to be checked rather than assumed.

Then they push again

It's already on an aggregate table, properly partitioned, and scans 200MB. Still 90 seconds.

Then it isn't an I/O problem and I'd stop looking at the scan. 200MB should be sub-second, so the time is going into computation, coordination, or the client.

Candidates: a shuffle-heavy operation on a small table — a COUNT(DISTINCT) or a window over a large grouping can still be expensive on modest data; a cross join or an accidental fan-out producing a large intermediate from small inputs; a correlated subquery executing per row; or a result set so large that the time is in serialising and transferring it to the BI tool rather than computing it.

Outside the query: queueing behind other workloads, cluster cold-start if it's serverless and scaling from zero, or the dashboard issuing many queries sequentially where the 90 seconds is the sum rather than one query.

I'd get this from EXPLAIN ANALYZE, which attributes time per operator and would settle it in one run. The distinction I'm trying to make is whether the 90 seconds is inside the engine at all — because if the query executes in two seconds and the dashboard takes 90, no amount of SQL tuning helps.

02
Someone added a BROADCAST hint six months ago. Should you remove it?
Neither "yes" nor "no" — find out what it's assuming.
What a strong answer covers

I'd want to know what data assumption it encodes before touching it, because both keeping and removing it blindly are risky.

The hint freezes a decision that the optimiser would otherwise make from current statistics. It was presumably right when written — the broadcast side was small and the optimiser was choosing sort-merge, perhaps due to stale statistics. The question is whether that side has grown since. In adtech, dimension tables like campaigns and creatives grow monotonically, so a hint written six months ago is exactly the kind that becomes an OOM.

So: measure the current size of the broadcast side. If it's still comfortably small, I'd consider removing the hint and checking whether the optimiser now chooses broadcast on its own — with AQE and fresh statistics it very likely will, and then the plan adapts as data changes instead of being pinned. If the optimiser still gets it wrong, keep the hint but add a comment stating the assumption and, ideally, a data-quality check that alerts when that table exceeds the threshold.

What I wouldn't do is remove it because hints are unfashionable, without checking. Somebody added it for a reason and the reason may still hold.

Then they push again

There's no test coverage and the query is in a nightly job that finance depends on. Now what?

Then the change management matters more than the optimisation, and I'd slow down rather than push a plan change into a finance-critical path.

Concretely: run the modified query alongside the existing one on a recent partition and diff the outputs to byte-level equality before changing anything in production. A plan change shouldn't alter results, but broadcast-versus-merge differences have surfaced genuine bugs elsewhere — null handling in join keys, for instance — and finding that in a comparison is much better than finding it in a month-end close.

Then I'd ask whether this is worth doing at all right now. If the job runs nightly with hours of headroom and the hint isn't currently causing a problem, the expected value of the change is low and the downside is a finance incident. I'd log it as known technical debt with the specific risk noted — that table grows and this will eventually OOM — and set a monitor on the table size so we act before it breaks rather than during a close.

That's the honest answer: the right time to fix it is when we have a test harness or when the monitor fires, not on a Tuesday because we noticed it.

03
Two queries, same result, one scans 40GB and one scans 400GB. Both look reasonable. What's the likely difference?
Think about what defeats pruning silently.
What a strong answer covers

Most likely one of them defeats partition pruning while looking correct. The usual mechanisms:

  • A function wrapping the partition column — WHERE date(event_ts) BETWEEN ... instead of a range on the partition column itself. Semantically identical, and the engine can no longer map the predicate to directories.
  • The filter derived from a subquery or join rather than a literal, so the partition list isn't known at planning time. Some engines handle this with dynamic partition pruning; many don't.
  • Filtering on event_time but partitioned on event_date, with no correlation declared. Hidden partitioning in Iceberg solves this; a Hive-style table does not.
  • A type mismatch forcing an implicit cast on the partition column.

The other strong candidate is projection: one selects six columns and the other does SELECT * somewhere in a CTE, so the scan reads every column of a very wide table even though the final output is narrow. On bid requests that alone easily accounts for a 10× difference.

I'd confirm by comparing the scan nodes in both plans — partitions read and pushed filters — which shows it immediately.

Then they push again

It's the SELECT * in a CTE. The author says it doesn't matter because they filter columns at the end.

It matters, and the reason is worth explaining precisely rather than just asserting. Column pruning is a planner optimisation that pushes the required column set down to the scan — and it works in many cases, which is why the author's mental model has survived. But it breaks when something between the CTE and the final projection forces materialisation of the full row: a CTE that's materialised rather than inlined, a UDF over the whole row, certain window functions, or a join whose plan doesn't propagate the pruning.

So sometimes it costs nothing and sometimes it costs 10×, and which one you get depends on engine version and plan shape rather than on anything visible in the query. That's the actual argument: not that SELECT * is always slow, but that it makes performance non-deterministic across changes nobody is tracking.

The evidence that settles it is right there — the two plans show different bytes scanned for the same result. I'd show them that rather than argue from principle, since a measured 10× on their own query is more persuasive than a rule.

Say it in sixty seconds
  1. Read plans bottom-up: scan nodes and pushed filters first, then exchanges, then join operators, then estimate-vs-actual rows.
  2. Read less, then shuffle less, then shuffle better — in that order.
  3. Functions on the partition column, subquery-derived filters, and type mismatches all defeat pruning silently.
  4. Bad join order is usually stale statistics; AQE re-plans from runtime shuffle stats.
  5. Hints freeze a data assumption — last resort, and they need a comment and a monitor.
  6. Check the non-query causes: small files, queueing, cold cache, result size, or querying the wrong table entirely.
What a weak answer sounds like
  • Optimising the SELECT list before checking what's scanned.
  • Never mentioning the query plan.
  • Adding hints as a first move.
  • Not knowing that COUNT(DISTINCT) is the expensive part of an otherwise cheap query.
  • Treating a caching layer as the fix for a query reading the wrong table.

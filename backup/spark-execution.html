03
Distributed execution

From DAG to shuffle

Every Panel 2 conversation eventually lands here. You will not be asked to define Spark — you will be handed a slow job and asked why. The skill is reading a symptom backwards to a physical cause.

The three-layer mental model

Hold Spark in three layers and almost every question resolves cleanly.

Logical layer. Your DataFrame operations build an unevaluated plan. Nothing runs. Transformations are lazy; only an action (write, collect, count) triggers execution. This is why an error in your logic often surfaces only at the write.

Physical layer. Catalyst optimises the logical plan and picks physical operators — which join strategy, where to insert an Exchange (a shuffle). The result is a DAG of stages. A stage is a maximal run of operations that can happen without moving data between executors.

Execution layer. Each stage becomes a set of tasks, one per partition, scheduled onto executor cores. Stages run in dependency order; tasks within a stage run in parallel.

The sentence that anchors everything

A stage boundary exists wherever a record has to move from the partition it is in to a different partition. That movement is the shuffle. Everything expensive is downstream of that one fact.

Narrow dependencies — map, filter, select, withColumn — each output partition reads exactly one input partition, so they fuse into a single stage with no data movement. Wide dependencies — groupBy, join, distinct, repartition, window functions — each output partition may need records from every input partition, so a shuffle is unavoidable.

What a shuffle physically does

This is the question behind the question. Be able to narrate it as a sequence of disk and network events, not as a diagram.

  1. Map side. Each task partitions its output by hash of the shuffle key into as many buckets as there will be reduce partitions. It sorts/spills these to local disk as shuffle files. If the in-memory buffer fills, it spills early — this is shuffle spill, and it is the single most common cause of a slow stage.
  2. The boundary. The stage completes. Nothing proceeds until every map task has written its files, which is why one straggler task blocks an entire stage.
  3. Reduce side. Each reduce task fetches its bucket from every map task's local disk across the network, merges the streams, and applies the aggregation or join.

So a shuffle is: serialize → write to local disk → N×M network fetches → merge. It is disk-bound and network-bound, and it scales with the product of partition counts on both sides.

Why reduceByKey beats groupByKey

groupByKey shuffles every record. reduceByKey (and agg on a DataFrame) applies a map-side combine first — it pre-aggregates within each partition, so only one partial result per key crosses the network. On a high-cardinality key with many records per key, that is often an order of magnitude less shuffle. The DataFrame API does this for you; the point of knowing it is diagnosing why a hand-rolled UDF-based aggregation is slow.

From first principles

You can derive the whole cost model from two facts. First, a network round trip is roughly a thousand times slower than a memory access, and disk sits in between. Second, the receiving task cannot begin until it knows every sender has finished — because it has no way to know whether more records for its key are still coming.

Those two facts force the design. Data must be materialised somewhere before it moves, because the receiver isn't ready to consume it in real time; local disk is the cheapest durable place. And the barrier must be global, because partial knowledge of a key is useless for an aggregation.

Everything else follows: the shuffle is expensive because it is bounded by disk and network rather than CPU; one slow map task blocks everything because the barrier is global; and map-side combine helps enormously because it reduces the bytes that must cross the slow layer, not the work done at either end.

Join strategies and how Catalyst chooses

StrategyMechanismUse whenFails when
Broadcast hash joinSmall side shipped whole to every executor; no shuffle of the large sideOne side fits comfortably in executor memory (default threshold ~10 MB, commonly raised)Small side is bigger than you thought → driver OOM or executor OOM
Sort-merge joinBoth sides shuffled on the join key, sorted, mergedTwo large tables; the default for big-to-bigSkewed keys → one reduce task gets everything
Shuffle hash joinBoth shuffled; one side built into a hash table per partitionOne side much smaller but still too big to broadcast, and not pre-sortedBuild side doesn't fit in a partition's memory

Bucketing is the way to avoid the shuffle entirely: if both tables are pre-bucketed on the join key with the same bucket count, matching keys are already co-located and the join becomes narrow. It is the right answer when you join the same two large tables repeatedly, and the wrong answer for a one-off.

Adaptive query execution

AQE re-plans at runtime using actual shuffle statistics. It coalesces too-many small post-shuffle partitions, converts a sort-merge join to a broadcast join when it discovers a side is small, and splits skewed partitions. Know it — but do not let it be your whole answer. AQE handles skew it can detect after the fact; it does not fix a badly chosen partition key.

Skew: the interview's favourite failure

Skew is when the distribution of your shuffle key is uneven, so one reduce task receives disproportionately many records. In adtech this is guaranteed: a handful of campaigns or publishers or a null device ID carry a huge fraction of rows.

Detecting it

  • Task duration distribution within one stage: 199 tasks finish in 30s, one runs for 40 minutes.
  • Shuffle read size per task, same shape.
  • Spill metrics concentrated on one or two tasks.
  • Offline: SELECT key, count(*) ... ORDER BY 2 DESC LIMIT 20 on the join key. Do this before designing, not after failing.

Fixing it

  • Salting. Append a random suffix 0..N to the hot key on the large side; explode the small side into N copies, one per salt. Turns one huge partition into N moderate ones. Cost: N× the small side.
  • Isolate hot keys. Split the job: broadcast-join the top-k hot keys separately, sort-merge the long tail, union the results. Often cleaner than salting because it doesn't inflate anything.
  • Filter the garbage. A large fraction of real-world skew is a null or sentinel ID (0000-0000, empty string). Those rows usually should not be joined at all.
  • Pre-aggregate. If the downstream need is a count, aggregate before the join so the hot key carries one row instead of a billion.
  • AQE skew join for the cases it can catch automatically.

Partitioning and the small-files problem

Two different meanings of "partition" and interviewers will test whether you conflate them.

In-memory partitions are units of parallelism. Too few and you underuse the cluster and risk OOM; too many and scheduling overhead dominates. spark.sql.shuffle.partitions defaults to 200, which is wrong for almost every real workload — a rough target is 2–4× total executor cores, with each task handling something in the low hundreds of MB.

On-disk partitions are directory layout, e.g. /dt=2026-08-09/hour=14/. These enable partition pruning: a query filtered on dt reads only matching directories.

repartition(n) does a full shuffle and gives even partitions. coalesce(n) avoids a shuffle by merging adjacent partitions, so it is cheap but can leave you with uneven sizes — and pushing coalesce(1) up the plan can collapse the parallelism of the entire upstream stage. That last point is the one people miss.

Small files

Writing hourly partitions from a 2000-partition job yields 2000 tiny files per hour. Every downstream reader then pays per-file open cost and the metastore or listing call becomes the bottleneck. Fix with a repartition before write sized to your target file (128–512 MB), or a scheduled compaction job.

From first principles

Why should partition count track executor cores rather than data size? Because a partition is the unit of work handed to one core, so the question is really: how many pieces should the work be cut into?

Too few pieces and cores sit idle — with 200 partitions on 500 cores, 300 cores do nothing. Too many and per-task scheduling overhead, which is fixed per task, starts to dominate the useful work in each. The optimum is a small multiple of core count: enough pieces that every core stays busy and stragglers can be absorbed, few enough that overhead stays negligible.

The data-size constraint enters separately: whatever the count, each partition must fit in the memory available to one task, or it spills. So you take the larger of the two requirements.

Reading a slow job backwards

Rehearse this as a decision procedure, because you will be handed a symptom.

Say "I'd open the Spark UI and look at the stage's task duration distribution first" early. It signals you have actually debugged a cluster rather than read about one.

Pushback

Now defend it

Each of these is a real interrupt. Commit to an answer before you reveal — reading the model answer without having tried is how you end up recognising the material but not being able to produce it.

01
Your job has a groupBy on campaign_id over 10 billion impression rows and it takes four hours. What is your first hypothesis and how do you confirm it?
They are testing whether you jump to a fix or to a diagnosis.
What a strong answer covers

Lead with diagnosis, not remedies. First hypothesis is skew on campaign_id, because ad campaign volume is heavy-tailed by nature — a handful of campaigns dominate delivery.

Confirm in two ways. In the Spark UI, look at the aggregating stage's task duration and shuffle-read distributions; skew shows as a small number of tasks with vastly larger read sizes. Independently, run a cheap frequency count on the key over a sample to see the actual distribution and identify the top keys.

Only then choose. If it is a few hot campaigns, isolate them and process separately. If it is a null or sentinel campaign ID, filter it. If the aggregation is associative (counts, sums), confirm map-side combine is happening — a Python UDF-based aggregate would defeat it and shuffle raw rows.

Then they push again

Suppose the distribution is fine — roughly uniform. Now what?

Then the cost is volume, not imbalance, and I shift to the other levers. Check partition count against cluster cores — a default of 200 on 10B rows means each task handles tens of millions of rows and almost certainly spills. Check spill metrics to confirm. Check whether the full row width is being shuffled when only a few columns are needed; projecting early cuts shuffle bytes directly. Check whether the source scan is reading all columns and all partitions, or pruning. And question the framing: if this aggregate is recomputed daily over the same historical data, the real fix is incremental aggregation over the new partition rather than a full recompute.

02
You said you would broadcast the smaller table. It is 800 MB. Defend that.
The honest answer is that you probably shouldn't.
What a strong answer covers

I would not broadcast 800 MB by default. Broadcast means the driver collects the table and ships a full copy to every executor, so the real cost is 800 MB × executor count in memory, plus driver pressure while it is assembled. On a 50-executor cluster that is 40 GB of duplicated data competing with execution memory.

What I would do instead: check whether 800 MB is the actual join-relevant size. If I only need two columns from that table, project first — that might land at 60 MB, which is comfortably broadcastable. If it genuinely needs to be that wide, sort-merge join, or bucket both tables on the key if this join is recurring.

Then they push again

Your teammate raised autoBroadcastJoinThreshold to 1 GB and the job got faster. Were they wrong?

Faster today, fragile tomorrow. They optimised for the current data size and cluster shape without a guardrail. The failure mode is silent: the dimension table grows 30% next quarter, the broadcast now exceeds executor memory, and you get an OOM in a job that had been stable for months — and the stack trace won't obviously say 'your reference table grew'. If we want that behaviour, I'd rather rely on AQE converting the join at runtime based on real statistics, or set the threshold deliberately with a monitored size check on the dimension table so it fails loudly at the right place.

03
Explain why coalesce(1) before writing a report table brought down a job that previously worked.
The trap is thinking coalesce is always the cheap option.
What a strong answer covers

Because coalesce does not insert a shuffle, the reduced partition count propagates backwards through the stage. It doesn't merge 200 computed partitions at the end — it makes the whole preceding stage run with a single task, so all the upstream computation collapses onto one core and one executor's memory. That is both a massive loss of parallelism and a likely OOM.

If the goal is genuinely one output file, use repartition(1), which forces a shuffle and preserves upstream parallelism, at the cost of the shuffle itself. Better still, question the requirement: needing exactly one file is usually a downstream consumer limitation worth fixing rather than accommodating.

Then they push again

So is coalesce ever the right call?

Yes — when reducing partition count after a filter that removed most rows, and where the reduction is modest. Going from 2000 partitions to 500 after filtering 95% of data avoids writing 2000 near-empty files, and the parallelism you give up is parallelism you no longer need. The rule of thumb: coalesce is safe when you are shrinking modestly and the upstream work is already cheap; it is dangerous when the ratio is extreme or the upstream work is heavy.

04
Walk me through what happens between the last task of stage 3 finishing and the first task of stage 4 starting.
They want the physical events, in order.
What a strong answer covers

Stage 3's tasks have each been writing shuffle output to local disk on their executor, partitioned by hash of the shuffle key into one bucket per stage-4 partition, with an index file so any bucket can be located. When the final stage-3 task completes, it registers its map output location with the driver's shuffle tracker.

The driver now has the complete map-output registry and schedules stage 4. Each stage-4 task queries where its bucket lives, then issues fetch requests to every executor that ran a stage-3 task — so the fetch pattern is all-to-all, M reducers × N mappers. Fetched blocks are merged, spilling to disk if they exceed the reducer's memory, and only then does the actual aggregation or join logic run.

Two consequences worth naming: nothing in stage 4 can start until the slowest stage-3 task finishes, and if an executor is lost after writing shuffle files, those map outputs are gone and the corresponding stage-3 tasks must be recomputed.

Then they push again

How does Spark recover if an executor dies mid-way through stage 4?

It recomputes from lineage. The driver knows the DAG, so it reschedules the lost stage-4 tasks on surviving executors — those can re-fetch from the still-intact shuffle files. The expensive case is losing an executor that held stage-3 shuffle output, because that output is not replicated: Spark must re-run those map tasks to regenerate it, which can cascade backwards. This is exactly what checkpointing addresses — truncating lineage by materialising to reliable storage so recovery doesn't replay the whole chain. For very long pipelines, a deliberate checkpoint after an expensive wide stage is cheap insurance.

05
The pipeline runs in 40 minutes on Monday and 6 hours on Tuesday. Same code. Go.
Don't guess a single cause — show a search strategy.
What a strong answer covers

Same code means something in the data or environment changed, so I'd bisect rather than speculate.

  • Data volume and shape. Compare input row counts and per-key distributions across the two days. A single advertiser launching a huge campaign turns a balanced join into a skewed one overnight.
  • Plan change. Pull the physical plan for both runs. A dimension table crossing the broadcast threshold silently flips a broadcast join to sort-merge — same code, entirely different execution.
  • File layout. An upstream producer changing its write pattern can turn 200 files into 200,000, and now the job spends its time listing.
  • Cluster. Fewer executors granted, noisy neighbours, spot reclamation causing recomputation.
  • Late-arriving data triggering a wider backfill window than usual.

The Spark UI comparison between the two runs answers most of this in minutes: same stage count or not, where the time moved to.

Then they push again

You have no access to Monday's Spark UI — the history server only retains 24 hours. What now?

Then I work from what persists. Input file counts and sizes are still on storage, so I can compare the physical footprint of both days directly. Table statistics or a cheap count per key gives me the distribution comparison. Job-level metrics in whatever scheduler ran it (Airflow duration history, cluster autoscaling logs) tell me whether the resource envelope changed. And this is the moment to say the systemic thing: retaining only 24 hours of history is the actual bug here. I'd want event logs persisted to object storage and a few job-level metrics — input rows, shuffle bytes, max task duration — emitted to our metrics system on every run, so the next occurrence is a chart rather than an investigation.

06
Why not just use a bigger cluster?
A cost-and-judgment question wearing a technical costume.
What a strong answer covers

Sometimes that is the right answer, and I'd say so rather than reflexively optimising. If a job runs monthly and adding nodes for twenty minutes costs less than a day of engineering time, scale it up and move on.

But it doesn't help for the failure modes that matter most. Skew doesn't improve with more nodes — the bottleneck is one task on one core, so extra executors sit idle. Small-file listing overhead doesn't improve; that is driver-side. And a job that shuffles far more than it needs to will shuffle proportionally more on a bigger cluster, so cost scales with the waste.

The judgment is: scale up for volume problems, fix the plan for imbalance and layout problems.

Then they push again

How would you decide, concretely, whether this job is worth optimising?

Compare marginal cost against marginal engineering time, with frequency as the multiplier. Cluster cost per run × runs per month gives an annual figure. If a job costs a few hundred dollars a year, optimising it is a poor use of an engineer regardless of how ugly it is. If it is tens of thousands, or if its runtime sits on the critical path for a downstream SLA — a reporting deadline, a model refresh — then latency has a business cost beyond compute and the calculation changes. I'd also weight fragility: a job that is currently cheap but one data-growth increment away from OOM is worth fixing before it pages someone.

Say it in sixty seconds
  1. A stage boundary is where records must move between partitions. That movement is the shuffle: partition by hash, write to local disk, fetch all-to-all, merge.
  2. Narrow ops fuse into one stage; wide ops (join, groupBy, distinct, window) force a shuffle.
  3. Broadcast when one side is genuinely small after projection; sort-merge for big-to-big; bucket if the same join recurs.
  4. Skew shows as one task 50× slower. Fix by isolating hot keys, salting, filtering sentinels, or pre-aggregating.
  5. Partition count should track executor cores, not the default 200. coalesce propagates backwards; repartition shuffles.
  6. Debug order: task duration distribution, then spill, then plan diff, then file layout.
What a weak answer sounds like
  • Describing Spark as "in-memory so it's fast" — a decade out of date and signals no operational experience.
  • Reaching for a fix before naming a diagnosis.
  • Answering every performance question with "enable AQE" or "add executors".
  • Confusing in-memory partitions with on-disk partition directories.
  • Not mentioning the Spark UI at all — it's the first thing a practitioner opens.

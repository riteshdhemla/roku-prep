Query design

SQL that survives ten billion rows

Neither of your repos contains any SQL, and a data-heavy panel will very plausibly ask you to write some live. The patterns below are the ones adtech questions actually reduce to.

Window functions, the whole vocabulary

Almost every non-trivial analytics question is a window function question. Know the frame syntax cold, because hesitating here is very visible.

<fn> OVER (
  PARTITION BY campaign_id      -- reset the calculation per group
  ORDER BY event_time            -- ordering within the group
  ROWS BETWEEN 6 PRECEDING AND CURRENT ROW   -- the frame
)
  • ROW_NUMBER() — unique sequential, ties broken arbitrarily. The dedup workhorse.
  • RANK() / DENSE_RANK() — ties share a value; RANK leaves gaps, DENSE_RANK doesn't.
  • LAG(col, n) / LEAD(col, n) — previous/next row's value. Sessionization and gap detection.
  • SUM(x) OVER (... ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) — running total.
  • FIRST_VALUE / LAST_VALUE — watch the frame; LAST_VALUE defaults to a frame ending at the current row, which surprises people.
ROWS vs RANGE

ROWS counts physical rows; RANGE counts logical values of the ORDER BY expression, so tied values collapse into the same frame. Getting a rolling 7-day average wrong because of this is a classic silent bug.

Deduplication

Impression logs arrive with duplicates from retries, at-least-once delivery, and client-side double-fires. The canonical pattern:

WITH ranked AS (
  SELECT *,
         ROW_NUMBER() OVER (
           PARTITION BY event_id
           ORDER BY ingest_time ASC
         ) AS rn
  FROM impressions
  WHERE event_date = DATE '2026-08-09'
)
SELECT * EXCEPT(rn) FROM ranked WHERE rn = 1;

Points to volunteer:

  • Pick the earliest deliberately. Keeping the first arrival is idempotent under replay; keeping the latest is not, because a re-run can change the answer.
  • If there is no event_id, construct a deterministic key from the fields that define identity — device, campaign, creative, and a truncated timestamp. Say out loud that this is a heuristic and can collapse genuine rapid repeat impressions, which is a real cost.
  • Window boundaries leak. Deduplicating within a single day's partition misses a duplicate that arrived just after midnight. Either dedup over a trailing window wider than your expected retry delay, or keep a persistent seen-set (Bloom + exact check) across boundaries.

Sessionization

Group a user's events into sessions separated by an inactivity gap. This is the most-asked SQL pattern in this space, and it is worth being able to write without thinking.

WITH gaps AS (
  SELECT device_id, event_time,
         CASE WHEN event_time - LAG(event_time) OVER (
                     PARTITION BY device_id ORDER BY event_time
                   ) > INTERVAL '30' MINUTE
              OR LAG(event_time) OVER (
                     PARTITION BY device_id ORDER BY event_time
                   ) IS NULL
              THEN 1 ELSE 0 END AS is_new_session
  FROM events
),
marked AS (
  SELECT *,
         SUM(is_new_session) OVER (
           PARTITION BY device_id ORDER BY event_time
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
         ) AS session_seq
  FROM gaps
)
SELECT device_id, session_seq,
       MIN(event_time) AS started_at,
       MAX(event_time) AS ended_at,
       COUNT(*)        AS events
FROM marked
GROUP BY device_id, session_seq;

The idea worth naming: a running sum over a boolean gap-flag becomes a session identifier. That trick generalises to any "group consecutive runs" problem.

Attribution and the last-touch join

Given conversions and a history of touchpoints, credit the conversion to a prior touch within a lookback window.

SELECT c.conversion_id, c.device_id, c.converted_at,
       t.campaign_id, t.touched_at
FROM conversions c
LEFT JOIN LATERAL (
  SELECT campaign_id, touched_at
  FROM touchpoints t
  WHERE t.device_id = c.device_id
    AND t.touched_at <= c.converted_at
    AND t.touched_at >= c.converted_at - INTERVAL '7' DAY
  ORDER BY t.touched_at DESC
  LIMIT 1
) t ON TRUE;

Where engines don't support lateral joins, the portable form is a range join followed by ROW_NUMBER() ... ORDER BY touched_at DESC and filtering to 1.

The performance trap

An inequality join on touched_at has no equality predicate to hash on, so the engine may fall back to a nested loop or a range partition. Always co-partition on device_id first so the inequality is evaluated within a small group, and bound the window tightly — a 7-day window is 7 times cheaper than a 90-day one, and someone should be able to justify the number.

Handling skew inside SQL

Skew doesn't disappear because you wrote SQL instead of Spark code — the same shuffle happens underneath. Two patterns worth having ready:

Salting a skewed join

-- large side: add a random salt to the hot key
SELECT ..., campaign_id,
       CASE WHEN campaign_id IN (SELECT campaign_id FROM hot_keys)
            THEN CAST(FLOOR(RAND() * 16) AS INT) ELSE 0 END AS salt
FROM impressions
-- small side: replicate each hot row 16 times, one per salt
-- then join ON (campaign_id, salt)

Two-phase aggregation

Aggregate at a finer grain first (adding a random bucket to the group key), then aggregate the partials. Spreads a hot key across many tasks and only works for associative aggregates — sums and counts, not medians or distinct counts unless you carry a sketch.

General query hygiene at scale

  • Filter and project before joining, never after. Every column you drop early is shuffle bytes you don't pay for.
  • Always bound on the partition column, even when it feels redundant — unless the table format supports hidden partitioning and derives it for you.
  • COUNT(DISTINCT x) across a large grouping is a shuffle-heavy operation and doesn't roll up. Reach for an approximate function or a stored sketch.
  • Beware SELECT DISTINCT used to paper over a join that fans out — fix the join, don't dedupe the symptom.
Pushback

Now defend it

Each of these is a real interrupt. Commit to an answer before you reveal — reading the model answer without having tried is how you end up recognising the material but not being able to produce it.

01
Write me the query for daily unique devices and impressions per campaign for the last 30 days. Talk me through it.
They'll interrupt with "now make it fast" — get ahead of it.
What a strong answer covers
SELECT campaign_id, event_date,
       COUNT(*)                        AS impressions,
       APPROX_COUNT_DISTINCT(device_id) AS unique_devices
FROM impressions
WHERE event_date >= CURRENT_DATE - INTERVAL '30' DAY
GROUP BY campaign_id, event_date;

Narration worth giving alongside it: the partition filter comes first so we prune 30 directories instead of scanning history; only three columns are touched, so on a wide Parquet table we read a fraction of the bytes; and I've used the approximate distinct deliberately — exact COUNT(DISTINCT) requires shuffling every device ID and is the expensive part of this query.

I'd then flag the thing the question doesn't say: daily uniques are not summable into a 30-day unique. If anyone downstream adds this column up they will get a wrong and inflated number. If a range-level unique is needed, this should be a stored HLL sketch per day rather than a count.

Then they push again

It's still too slow for a dashboard that reloads every ten seconds.

Then the query is the wrong layer to optimise — no scan over raw impressions belongs on a ten-second refresh path. I'd materialise this as a daily aggregate table written once by the batch pipeline, with the sketch stored rather than the count, and point the dashboard at that. It's a few hundred thousand rows instead of billions, and the query becomes a trivial range scan.

If the freshness requirement includes today's partial data, I'd layer: the materialised table for closed days, plus a small streaming aggregate for the current day, unioned at read time. That's the standard shape and it's worth naming as such. What I'd want to avoid is caching the slow query, which papers over the architecture and gives you a stale-cache incident later.

02
Your sessionization query works on a sample and OOMs on the full table. Why?
Look at the window definition, not the logic.
What a strong answer covers

The window is PARTITION BY device_id ORDER BY event_time, so the engine shuffles all of a device's events to one task and sorts them. Two things break at scale.

First, skew: a bot, a test device, or a null device ID can have hundreds of millions of events, and that entire group must fit in one task's memory to be sorted. Second, if device_id is null or a sentinel for a meaningful fraction of rows, every one of those rows lands in a single partition.

Fixes, in order of what I'd try: filter null and sentinel device IDs before the window — they can't be sessionized meaningfully anyway; cap or separate abnormally high-volume devices and handle them apart; ensure the input is bounded to one day rather than all history; and raise the partition count so ordinary devices spread further, which helps the general case even though it doesn't help the single hot device.

Then they push again

You can't filter them — the bot traffic detection team needs those rows.

Then I'd separate the workload rather than force one query to serve both. Route high-volume devices — identified cheaply by a count threshold, or a Count-Min pass — into their own job where sessionization can be done with a different strategy or skipped entirely, since a device with a hundred million events doesn't have meaningful sessions in the product sense anyway. The normal-traffic path then runs clean.

I'd also question whether sessionization is what bot detection actually wants from those rows. Usually it wants the raw event stream and its own features, not sessions. Establishing that lets us stop paying a sessionization cost for rows where the output is meaningless — which is a better outcome than making the expensive query survive.

03
Give me the multi-touch attribution version of that last-touch query.
The SQL is a fan-out plus a weighting. The interesting part is the model choice.
What a strong answer covers

Structurally: instead of taking the single most recent touch, take all touches in the window and distribute fractional credit that sums to 1 per conversion.

WITH touches AS (
  SELECT c.conversion_id, t.campaign_id, t.touched_at,
         ROW_NUMBER() OVER (PARTITION BY c.conversion_id
                            ORDER BY t.touched_at) AS pos,
         COUNT(*)    OVER (PARTITION BY c.conversion_id) AS n
  FROM conversions c
  JOIN touchpoints t
    ON t.device_id = c.device_id
   AND t.touched_at BETWEEN c.converted_at - INTERVAL '7' DAY
                        AND c.converted_at
)
SELECT conversion_id, campaign_id,
       1.0 / n AS credit          -- linear
FROM touches;

Swap the credit expression for the model: position-based (40/20/40), time-decay (exp(-lambda * hours_before) normalised per conversion), or U-shaped.

The point I'd make unprompted: every one of these weightings is a convention, not a measurement. None of them establishes that the touch caused the conversion. If the question is which channel actually drove incremental conversions, MTA is the wrong instrument and the answer is a holdout experiment — that's stage 08.

Then they push again

The join fans out badly — some conversions have thousands of touches. How do you make it not explode?

Bound the fan-out explicitly rather than let the data decide. Practical measures: cap touches per conversion to the most recent k, which for most attribution models beyond the top few positions changes the answer negligibly while cutting the intermediate result dramatically; tighten the lookback window and make someone justify its length; and pre-aggregate touchpoints to one row per (device, campaign, day) before the join, since most models don't distinguish two impressions of the same campaign an hour apart.

Mechanically I'd also make sure the join is co-partitioned on device_id so the range condition is evaluated within small groups rather than driving a broadcast nested loop. And I'd check whether the thousand-touch conversions are real — a device with a thousand touches in seven days is often a bot or an identity over-merge, which loops back to stage 03.

04
When would you write this in SQL rather than in Spark's DataFrame API?
A judgment question about maintainability, not syntax.
What a strong answer covers

Almost always SQL, for anything that is fundamentally a transformation over tables. It is readable by analysts as well as engineers, it is portable across engines, it's easier to review in a pull request, and the optimiser sees the whole statement rather than a chain of opaque calls.

I'd reach for the DataFrame API when the logic is genuinely programmatic: constructing a query dynamically from configuration, iterating a graph algorithm, applying a Python model in a UDF, or unit-testing composable transformation functions in isolation. Those are cases where SQL becomes string manipulation, and string-built SQL is worse than either option.

The honest answer is that the two compile to the same plan, so this is a maintainability decision and not a performance one — and saying that explicitly is usually what the question is checking.

Then they push again

Our team writes everything as Python UDFs. What's your view?

I'd want to understand why before criticising it, since there's often a real constraint behind it. But my honest view is that it's a performance and observability problem worth addressing. A Python UDF forces serialisation of each row out of the JVM into a Python process and back, defeats Catalyst's ability to optimise across the operation, and blocks predicate and projection pushdown through it. It's frequently the single largest cost in a job.

Where a UDF is genuinely needed, vectorised (pandas/Arrow) UDFs recover a large fraction of the cost by batching. And a lot of UDFs in practice reimplement something the built-in functions already do — string parsing, date arithmetic, JSON extraction — so an audit usually finds easy wins. I'd frame it to the team as a measured comparison on one representative job rather than a style objection, because that's the version that actually changes behaviour.

Say it in sixty seconds
  1. Window functions: know PARTITION BY / ORDER BY / frame, and know ROWS vs RANGE.
  2. Dedup with ROW_NUMBER over a stable event key, keeping the earliest so replays are idempotent; watch partition-boundary leakage.
  3. Sessionize with LAG to flag gaps, then a running SUM of the flag as the session ID.
  4. Attribution is a bounded range join; co-partition on device and bound the window tightly or it degenerates into a nested loop.
  5. Filter and project before joining; bound on the partition column; avoid exact COUNT(DISTINCT) at scale.
  6. Salting and two-phase aggregation are the SQL-level answers to skew; two-phase only works for associative aggregates.
What a weak answer sounds like
  • Writing correct SQL but never mentioning what the engine does underneath.
  • Using COUNT(DISTINCT) over a huge grouping without flagging the cost.
  • Summing daily uniques into a period unique.
  • Presenting multi-touch attribution as if it measures causation.
  • SELECT * on a wide event table.

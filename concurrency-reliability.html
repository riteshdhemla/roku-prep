Concurrency & correctness

Two kinds of concurrency, one kind of failure

Panel 2 lists concurrency separately from distributed systems, and they are separate questions. One is about threads inside a process; the other is about correctness when machines fail independently.

Concurrency inside one process

Start by distinguishing the bottleneck, because the right primitive follows from it directly.

WorkloadRight tool in PythonWhy
I/O-bound (API calls, DB, file reads)asyncio, or a thread poolThreads release the GIL while blocked on I/O, so concurrency is real
CPU-bound pure PythonmultiprocessingThe GIL serialises bytecode execution; threads give no speedup
CPU-bound numericThreads are often fineNumPy/Arrow release the GIL inside C routines
Embarrassingly parallel over dataSpark / DaskThe problem is data movement, not thread scheduling

The GIL, precisely: CPython allows only one thread to execute Python bytecode at a time. It is released around blocking I/O and inside many C extensions. So threads help with waiting and not with computing. Recent CPython versions have introduced an optional free-threaded build removing the GIL, which is worth knowing exists — but do not assume the production environment uses it.

asyncio is cooperative single-threaded concurrency: one event loop, tasks that yield at await. It scales to very many concurrent I/O operations cheaply, and it has one lethal failure mode — a single blocking synchronous call inside a coroutine stalls the entire loop, including unrelated tasks. That is the bug to name.

The classic hazards

  • Race condition. Two threads read-modify-write shared state; one update is lost. In Python, even counter += 1 is not atomic.
  • Deadlock. Two threads each hold a lock the other needs. Prevent by acquiring locks in a globally consistent order, or by using timeouts and failing rather than waiting forever.
  • Livelock and starvation. Threads are active but making no progress, or one thread never gets scheduled a resource.
  • Thundering herd. A cache entry expires and a thousand requests simultaneously recompute it. Fix with a single-flight lock, request coalescing, or jittered expiry.
  • Unbounded queues. A producer faster than its consumer grows a queue until memory is exhausted. Always bound the queue; a bounded queue is backpressure.

Producer/consumer is the pattern most likely to be asked as a coding exercise: a bounded queue, N worker threads, a sentinel or event for shutdown, and explicit handling of what happens when a worker raises. The last part is what separates a working answer from a good one — an exception in a worker that silently kills the thread leaves the pipeline quietly half-broken.

Delivery semantics and exactly-once

Say this clearly, because it's frequently muddled: exactly-once delivery is not achievable over an unreliable network. What is achievable is exactly-once effect, built from at-least-once delivery plus idempotent processing.

  • At-most-once: fire and forget. Fast, loses data on failure.
  • At-least-once: retry until acknowledged. Never loses, may duplicate. The realistic default.
  • Effectively-once: at-least-once plus deduplication or idempotent writes.

The three mechanisms that get you there

Idempotency keys. Every event carries a stable ID assigned at the source. Writes become upserts keyed on it, so replaying a batch produces the same table state.

Deduplication with a bounded window. Keep a seen-set over a window wider than your maximum retry delay — Bloom filter for the cheap negative, exact store for confirmation. Bounded, because an unbounded seen-set is just the whole dataset again.

Transactional or atomic commit. Write output and consumer offset in one atomic operation, so you can never advance past data you didn't durably write. This is what Kafka transactions and table-format commits give you.

The pipeline-level version

Design every batch job so that re-running it for a given partition produces exactly the same result. Overwrite the partition rather than append to it, derive nothing from wall-clock time inside the job, and take the partition as a parameter. Then a backfill is just a re-run, and recovery stops being a special procedure.

Consistency, ordering, and time

Consistency models in one line each: strong — every read sees the latest write, at the cost of coordination latency; eventual — replicas converge, reads may be stale; read-your-writes — a useful middle ground where a client at least sees its own updates.

CAP in practice is less "pick two" than "when a partition happens, do you refuse writes or serve possibly-stale data". For ad serving the answer is almost always availability: a stale audience segment is much better than a failed ad request.

Ordering. Kafka guarantees order within a partition only. If per-user ordering matters, partition by user key. A global order across partitions doesn't exist, and designs that assume it break subtly under load.

Event time vs processing time. Event time is when it happened; processing time is when you saw it. Windowed aggregations should use event time, or your numbers shift whenever the pipeline lags. Watermarks are the mechanism: a heuristic assertion that no more events older than T will arrive, which lets a window close. The trade-off is direct — a longer watermark delay means more completeness and more latency, and data later than the watermark is dropped or routed to a late-data path. Have a position on which, because "we just drop it" is a real answer only if someone has agreed to it.

Failure, backpressure, and degradation

  • Backpressure. When a downstream is slower than upstream, the system must slow the producer rather than buffer indefinitely. Bounded queues, consumer-driven pull, and rate limits. Unbounded buffering converts a latency problem into an outage.
  • Retries with jittered exponential backoff. Fixed-interval retries synchronise clients into waves that keep a recovering service down.
  • Circuit breakers. After N failures, stop calling and fail fast, then probe periodically. Prevents a slow dependency from consuming all your threads.
  • Timeouts everywhere. An un-timed-out call is an unbounded resource hold. Most cascading failures start here.
  • Graceful degradation. Decide in advance what to do without a dependency: serve a default segment, skip personalisation, drop optional enrichment. Ad serving especially should never fail closed on an optional lookup.
Pushback

Now defend it

Each of these is a real interrupt. Commit to an answer before you reveal — reading the model answer without having tried is how you end up recognising the material but not being able to produce it.

01
Your Python service makes 500 outbound API calls per request cycle. It's slow. Threads or processes?
Name the bottleneck before the tool.
What a strong answer covers

Threads, or better, asyncio — because this is I/O-bound. The process spends nearly all its time waiting on network responses, and the GIL is released while waiting, so concurrency is real. Processes would add memory and IPC overhead to solve a problem that isn't CPU contention.

Concretely I'd use an async HTTP client with a bounded semaphore — say 50 concurrent — rather than firing all 500 at once, because unbounded concurrency just moves the failure to the other service or to file-descriptor exhaustion. Per-call timeouts, retries with jittered backoff, and a circuit breaker on the dependency.

I'd also ask the question behind the question: 500 calls per request cycle suggests an N+1 pattern. If the API supports batching, one batched call beats any amount of concurrency tuning, and that's the change I'd push for first.

Then they push again

You use asyncio and it's barely faster. What did you get wrong?

The most likely cause is a blocking synchronous call inside a coroutine — a requests call instead of an async client, a synchronous DB driver, a CPU-heavy JSON parse, or even a blocking DNS lookup. Any of those stalls the entire event loop, so tasks that look concurrent are effectively serial. That's the signature failure of asyncio and I'd check it first, by profiling event-loop blocking or simply auditing the call path for non-async libraries.

Other candidates: the concurrency limit is set too low; the bottleneck is the remote service rate-limiting or queueing us, in which case client concurrency is irrelevant; or connection-pool limits in the HTTP client cap effective parallelism below what we configured. The general lesson worth stating is that async gives you concurrency only over genuinely awaitable operations — wrapping blocking code in a coroutine doesn't make it non-blocking, and run_in_executor is the escape hatch when you must call something synchronous.

02
Make this impression pipeline exactly-once. Kafka in, aggregates out.
Correct the premise first, then build it.
What a strong answer covers

I'd start by reframing: exactly-once delivery isn't achievable across a network. What we can build is exactly-once effect, and the pieces are at-least-once delivery plus idempotent processing.

  • Source. Each impression carries an event_id assigned at emission — not generated in the pipeline, or a retry produces a new one and dedup fails.
  • Consumption. At-least-once with manual offset commits, committed only after the write is durable. Never auto-commit before processing.
  • Dedup. A seen-set over a window wider than the maximum retry or replay delay — Bloom filter as a cheap negative test, exact store to confirm. Bounded so it doesn't grow without limit.
  • Write. Idempotent by construction. Either upsert keyed on event_id, or make each batch overwrite a deterministic partition so re-running it replaces rather than accumulates.
  • Commit atomicity. Offset advance and output write in one transaction where the stack supports it, so we can't skip data we didn't write.

The property I'd want to state as the goal: re-running any partition produces byte-identical output. If that holds, recovery is just a re-run.

Then they push again

The aggregate is a running count in a key-value store. Upserts don't help — increments aren't idempotent. Now what?

Right, and that's the real difficulty — increment is the classic non-idempotent operation. Three routes, roughly in order of preference.

Make the aggregate derived rather than incremental: store deduplicated events and recompute the count for the affected window. Idempotent by construction, at the cost of recomputation.

Store the contributing IDs, not just the count — a sketch or a set per window — so re-adding a seen ID is a no-op. This is another reason mergeable sketches show up everywhere in this domain.

Make the write conditional: increment only if this event_id is not already recorded in a processed-set, with both in one atomic operation. Requires transactional support in the store, and the processed-set needs a bounded window.

Which one depends on the store's capabilities and the freshness requirement, and I'd want to know both before choosing rather than assert one.

03
Data arrives four hours late. Your hourly aggregate already closed. What do you do?
There is no free answer — pick a trade-off and own it.
What a strong answer covers

First I'd establish whether four hours is the tail or the norm, by measuring the distribution of ingest_time - event_time. Designing against an anecdote is how you get either a permanently laggy pipeline or a permanently wrong one.

Then the options, which are genuinely trade-offs rather than a right answer:

  • Extend the watermark to cover the late window. Correct, and it makes every number four hours late. Usually unacceptable for a live dashboard.
  • Close on time, reprocess later. Emit provisional results at the hour, then recompute affected partitions once late data settles. This is the standard answer, and it requires downstream consumers to tolerate numbers that change — which is a product decision, not an engineering one.
  • Route late data to a side path and apply corrections as deltas rather than recomputing.
  • Drop it, explicitly and with a metric on how much is being dropped. Legitimate if the volume is negligible and someone has agreed — illegitimate if it happens silently.

My default would be provisional-then-corrected, with a clearly labelled finality marker so consumers know which numbers are settled.

Then they push again

Finance built a report on the provisional numbers and it doesn't reconcile with the corrected ones. Whose problem is that?

Mine, at least partly — and I'd own that rather than deflect it, because "the data was labelled provisional" is technically true and practically useless if nobody noticed the label. If a consumer can build a report on non-final data without being aware of it, the interface failed.

The fixes are interface-level: expose finality as a queryable property rather than documentation, so a report can filter to settled partitions; publish a completeness or finality marker per partition that downstream jobs can wait on; and for a consumer like finance, provide a separate view that only exposes closed periods, so the provisional data isn't reachable by accident.

The broader principle I'd state is that data contracts have to be enforceable rather than advisory. Anything that depends on every consumer reading the documentation correctly will eventually break, and the incident will surface at the worst possible time — typically during a close.

04
Design a rate limiter for an ad-serving API. Multiple instances, no shared cache.
They want the algorithm and the coordination problem separately.
What a strong answer covers

Two decisions: the algorithm, and how state is shared.

Algorithm. A token bucket is usually right — it permits controlled bursts, which matches real traffic, and it's cheap: a token count and a last-refill timestamp per key, refilled lazily on access. A sliding-window counter is more precise about the rate but more state. Fixed windows are simplest and have the boundary problem, where 2× the limit passes across a window edge.

Coordination without shared state. Options in order of how much I'd want them:

  • Partition by key so each client's requests route to one instance, making local state authoritative. Clean if the load balancer supports consistent hashing on the key.
  • Divide the limit across N instances and enforce locally. Simple, but wastes capacity under uneven distribution, and adding an instance changes everyone's effective limit.
  • Approximate sharing — instances gossip counts on a short interval and converge, accepting a small overshoot bounded by the sync period.

For ad serving specifically I'd bias toward local enforcement with slight overshoot, because adding a coordination round trip to the serving path costs latency on every request to solve a problem that only matters at the margin.

Then they push again

What happens when an instance restarts and loses its buckets?

It fails open — briefly every client gets a fresh full bucket, so we can exceed the limit for one refill period on that instance. For a rate limiter protecting against accidental overuse that's acceptable; for one enforcing a paid quota it isn't, and the difference matters.

If it matters, the options are persisting bucket state to a local store with periodic snapshots (bounded loss, no serving-path cost), or moving to a shared store like Redis and accepting the latency and the new dependency. I'd want to know which failure is worse before choosing: over-serving briefly on restart, or adding a dependency whose own failure takes down ad serving entirely.

Worth stating plainly: a rate limiter that fails closed is often more dangerous than one that fails open, because now a restart or a Redis blip stops serving ads and losing revenue, to prevent a small overshoot. Fail-open is usually the correct default here and it should be a deliberate choice rather than an accident of implementation.

Say it in sixty seconds
  1. I/O-bound → asyncio or threads (GIL releases on I/O). CPU-bound pure Python → processes. Numeric → threads are fine.
  2. One blocking call inside a coroutine stalls the whole event loop — the signature asyncio bug.
  3. Exactly-once delivery doesn't exist; exactly-once effect does — at-least-once plus idempotent writes and bounded dedup.
  4. Make every batch job re-runnable to identical output: overwrite partitions, no wall-clock dependence, partition as a parameter.
  5. Kafka orders within a partition only; partition by the key whose order matters.
  6. Watermarks trade completeness against latency. Bounded queues are backpressure. Timeouts everywhere.
What a weak answer sounds like
  • Claiming a system achieves exactly-once delivery.
  • Choosing threads vs processes without naming whether the work is I/O- or CPU-bound.
  • Designing a streaming aggregate with no position on late data.
  • Unbounded queues or retries without jitter.
  • Treating a rate limiter or cache as infallible with no failure-mode discussion.

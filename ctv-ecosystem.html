Domain foundation

How a CTV ad actually gets served

Every Spark job and SQL query in the rest of this site operates on tables produced by this pipeline. If you can name where a row comes from and why it might be missing, duplicated, or wrong, your design answers stop being generic.

Both panelsDomainRead first

The request path, end to end

A viewer starts a show on a connected TV. Roughly this happens:

  1. Ad break signalled. The player or the streaming server reaches a cue point in the content — often an SCTE-35 marker carried in the stream.
  2. Ad request. The publisher's ad server is asked to fill a break. It carries device identifier, app/channel, content metadata, geo, and pod parameters (break duration, number of slots).
  3. Auction. The publisher's SSP issues an OpenRTB bid request to many DSPs. Each DSP decides whether to bid, at what price, with which creative. First-price is now standard. This produces a bid request log and a bid response log, both enormous — typically 10–100× the impression volume, since most requests don't become impressions.
  4. VAST response. The winner returns a VAST XML document: the creative's media file URLs plus a list of tracking URLs (beacons).
  5. Stitching or client playback. Either the client player fetches and plays the creative, or a server stitches it into the stream (see SSAI below).
  6. Beacons fire. As playback progresses, HTTP calls hit tracking endpoints: impression, start, firstQuartile, midpoint, thirdQuartile, complete, plus error beacons.
  7. Logs land. Beacon hits become the impression log — the billing-grade record. Everything downstream is derived from it.
The consequence for your pipelines

An impression is not a single event. It is a set of beacon events that must be assembled, deduplicated, and reconciled against the auction record. Most CTV data quality work is exactly this join.

Ad pods, and why they change every query

Linear TV has commercial breaks; CTV inherited them as pods. A single break might be 90 seconds holding four to six ad slots. This is the structural difference from web display, and it shows up everywhere.

  • Pod position matters. The first slot in a break performs differently from the last; queries that ignore pod_position mix incomparable inventory.
  • Competitive separation. Two car ads cannot share a pod. This is a constraint the decisioning system enforces, and a reason a bid can win the auction and still not serve.
  • Pod-level frequency. Capping must consider the break as a unit, not just the day — the same ad twice in one pod is a visible failure.
  • Partial pods. Unfilled slots are a fill-rate problem, and a break that ends early because the viewer abandoned produces truncated beacon sequences.

So the natural grain of a CTV impression table is (session, break, pod_position), not just (user, ad) — and a design that assumes one ad per request will get corrected.

SSAI, and the identity problem it creates

Server-side ad insertion stitches ads into the video stream on a server so the viewer sees one continuous stream and ad blockers can't distinguish content from ads. It is how most premium CTV inventory is delivered.

The cost is that the server, not the device, now sits between you and the viewer:

  • Beacons fire from the stitcher, so the source IP and user agent belong to the SSAI vendor's infrastructure rather than the household. If you build identity on IP, SSAI traffic collapses onto a handful of data-centre IPs — a classic cause of the million-device identity component from stage 03.
  • Identifiers must be passed explicitly through the request chain. Missing or malformed device IDs are common, and they arrive as nulls, zeros, or all-Fs sentinels.
  • Impression counting is server-asserted. A beacon means the stitcher believed the ad was delivered, which is not identical to the viewer watching it. Discrepancy reconciliation between publisher, SSP, and DSP counts is a permanent operational activity, and 2–10% gaps are normal.
Interview-ready line

"SSAI means the impression beacon originates from infrastructure, not from the household — so I'd treat IP as an unreliable identity signal on that traffic and require the passed-through device identifier, with the sentinel values denylisted."

Identifiers, co-viewing, and what "a user" means

CTV device identifiers are platform-specific: Roku's RIDA, Samsung's TIFA, Amazon's device ID, Vizio's, and so on — each resettable by the viewer, each namespaced per platform. There is no cross-platform cookie equivalent, which is precisely why identity graphs (stage 09) matter more here than on web.

ACR — automatic content recognition — is the other distinctive CTV data source: the TV fingerprints what is on screen, including linear broadcast, giving exposure data no ad server sees.

Two conceptual traps worth naming before an interviewer does:

The device is a household, not a person. One living-room TV is shared. Person-level targeting on a shared screen is an inference, not an observation, and any experiment randomised at the individual level leaks across the household.

Co-viewing means one impression reaches multiple people. Reach computed from device counts understates human reach, sometimes by 1.5–2×. Some measurement systems apply a co-viewing factor, usually panel-derived. If an interviewer asks how you'd compute reach and you answer "distinct devices" without flagging this, you've answered the web question.

Pushback

Now defend it

Each of these is a real interrupt. Commit to an answer before you reveal — reading the model answer without having tried is how you end up recognising the material but not being able to produce it.

01
Impressions in our log are 8% higher than the DSP's count for the same campaign. Where do you look?
Enumerate causes by where in the chain they arise.
What a strong answer covers

An 8% gap is within the normal band for CTV, so I'd frame it as reconciliation rather than a bug, then enumerate causes by position in the chain.

  • Counting point differs. We may count the impression beacon at ad start; they may count on a viewability or completion threshold. Different definitions, both correct.
  • Deduplication differs. Beacon retries are common; if we dedup on a 1-hour window and they dedup on the day, our number is higher.
  • Filtering differs. Invalid traffic exclusion, bot lists, and known-bad device sentinels are applied at different points and with different lists.
  • Timezone and day boundary. An 8% shift is consistent with a boundary offset if delivery is uneven across the day.
  • Loss in transit. Their beacon endpoint dropping requests under load shows up as our surplus.

Practically I'd reconcile on one campaign for one hour and trace a sample of specific impression IDs through both systems, rather than argue about aggregates — the mismatch is nearly always definitional and a hundred rows will show it.

Then they push again

It's not 8%, it's 40%, and only on one publisher.

Then it's a defect, not a definitional gap, and the single-publisher scoping is the most useful clue — it rules out anything in our shared logic and points at that integration.

The candidates I'd check in order: are they double-firing beacons, either from a misconfigured VAST wrapper or a player retrying without an idempotency key? Is SSAI in the path re-requesting on stream restarts, so one viewer session generates multiple impression events? Is the device identifier absent for that publisher, which would break our dedup entirely because we'd have no key to dedup on? And is the publisher's traffic disproportionately from one IP range, suggesting a stitcher or a proxy inflating what looks like distinct sessions?

The fastest discriminator is to pull raw beacons for a handful of sessions from that publisher and look at the actual sequence. If one impression beacon appears five times with the same parameters seconds apart, that's a retry problem; if it appears with distinct IDs, it's a re-request problem, and those have different fixes.

02
Design frequency capping for CTV. What's different from web?
Two things: the shared screen, and the pod.
What a strong answer covers

Two structural differences change the design.

The unit is a household, not a person. The device identifies a TV that several people watch. So a cap of three per day is a cap on household exposures, and if the product intent is per-person, we cannot deliver that from device data alone — we'd need a co-viewing model, and I'd want that stated rather than implied.

Pods create a second capping level. Beyond daily caps, you need per-break constraints: no repeat of the same creative in a pod, and typically no repeat within a content session. That's a decisioning-time constraint evaluated across the slots in the break simultaneously, not a simple counter.

Mechanically: a per-(device, campaign, day) counter with TTL for the daily cap, plus per-pod state held for the duration of the break. Given ad serving is latency-critical and distributed, I'd accept slight overshoot from eventual consistency across regions rather than put a coordination round-trip in the serve path — and I'd size the overshoot against the contractual meaning of the cap.

Then they push again

Same household streams on the TV and on a phone. Same cap?

That's the identity graph question, and the answer depends on what we can defensibly link. If the phone and TV resolve to the same household in the graph — via shared account login, which is the strong signal, or shared residential IP, which is weaker — then the cap should apply at the household level and be enforced across both.

But I'd flag the precision risk. IP-based linking on mobile is unreliable: the phone leaves the house and joins other networks, carrier NAT groups unrelated households together, and SSAI traffic doesn't carry a household IP at all. Over-merging here means we cap a household we've wrongly assembled and under-deliver to real viewers.

So my proposal would be to enforce cross-device capping only on deterministic links (authenticated account), and treat probabilistic links as advisory — usable for reporting reach, not for a hard delivery constraint. That's the general precision-versus-recall posture from the identity stage, applied to a case where the cost of a wrong merge is measurable in undelivered impressions.

03
Why is your bid request table a hundred times bigger than your impression table, and what do you do about it?
They want to see whether you'd store it all.
What a strong answer covers

Because every ad opportunity is offered to many DSPs and most opportunities never serve — no bid clears, another bidder wins, the pod fills elsewhere, or the viewer abandons. The funnel from request to impression is steep by design.

What I'd do with it depends on the use case, and I wouldn't store it uniformly:

  • Sample for analytics. A deterministic hash-based sample — say 1% keyed on request ID — preserves distributional properties for most analysis at 1% of the cost. Deterministic so the sample is stable across reruns and joinable.
  • Keep aggregates at full fidelity. Bid rate, win rate, clearing price distributions by segment, computed on the full stream and stored small.
  • Retain full raw briefly — days, not months — for debugging and dispute, then expire.
  • Project aggressively. Bid requests are very wide; most analysis needs a dozen fields. A narrow derived table costs a fraction.

The thing I'd push back on is the reflex to keep everything at full resolution forever, which is where most of the storage bill in this domain comes from.

Then they push again

Someone needs to investigate why a specific advertiser lost a specific auction three months ago. Your sample doesn't contain it.

Then the sample was the wrong tool for that need, and I'd rather design for it explicitly than widen retention globally. Options, roughly in cost order.

Keep a targeted full-fidelity slice: retain all requests for a small set of high-value advertisers or deals, where disputes are actually likely, at full resolution for a longer window. Most auction forensics is concentrated in a handful of relationships.

Keep loss reasons in aggregate at full coverage: we don't need every bid request row to answer "why do we lose this advertiser's auctions" — a per-segment loss-reason breakdown at full coverage answers the pattern question, and the pattern is what actually informs a fix.

Tiered storage rather than deletion: full raw compressed on cold object storage for the compliance window, expensive and slow to query but present when a genuine dispute arises.

The general point I'd make is that "we might need it someday" isn't a retention policy. I'd want to know which specific questions must be answerable at what horizon, then size retention to those, because that conversation usually reveals that three months of full raw was never actually required.

04
How would you compute reach for a CTV campaign? Be careful.
The careless answer is distinct devices.
What a strong answer covers

The mechanical answer is distinct devices exposed, via an HLL sketch per campaign per day so ranges merge — but I'd immediately qualify that this is device reach, and it is not what an advertiser means by reach.

Three corrections stand between device count and human reach:

  • Device to household. One household may have several CTV devices. Without resolving them, we overstate household reach. That's the identity graph.
  • Household to people. Co-viewing means one impression can reach two or three people. This understates human reach and is typically corrected with a panel-derived co-viewing factor that varies by daypart and genre — primetime co-viewing is much higher than late night.
  • Cross-platform. The same person reached on CTV and mobile is one person, which requires cross-device identity.

So I'd deliver device reach as the measured quantity, household reach as the resolved quantity, and human reach as a modelled estimate with its assumptions stated. Conflating the three is how you end up in a reconciliation argument you can't win.

Then they push again

The advertiser only cares about one number. Which do you put on the report?

Household reach as the headline, with device and estimated person reach available alongside — and I'd argue for that rather than just pick one.

Household is the right default because it's the unit we can actually measure with defensible precision: it's derived from observed data plus deterministic linking, not from a panel-derived model. Device reach is an implementation artifact that no advertiser thinks in, and it moves when a household buys a second TV, which makes it a confusing number to plan against. Person reach is the one they conceptually want, but it carries modelling uncertainty that compounds with our identity uncertainty, and putting a modelled number alone on a report invites disputes we can't resolve with data.

What I'd insist on regardless of which number wins is that the definition is fixed, documented in a semantic layer, and identical across every surface — dashboard, API, and invoice. The failure that actually damages trust isn't picking the imperfect metric; it's the same word meaning different things in two places.

Say it in sixty seconds
  1. Request → OpenRTB auction → VAST response → playback → beacons. The impression log is assembled from beacons, not emitted as one event.
  2. Pods mean the grain is (session, break, pod_position); position, competitive separation, and per-pod frequency all follow.
  3. SSAI fires beacons from infrastructure, so IP is not a household signal on that traffic and identifiers must be passed explicitly.
  4. Device identifiers are platform-specific and resettable; there is no cross-platform cookie, which is why the identity graph carries the load.
  5. A device is a household, and co-viewing means one impression reaches more than one person — device reach is not human reach.
  6. Bid requests dwarf impressions; sample deterministically, aggregate at full fidelity, retain raw briefly.
What a weak answer sounds like
  • Designing as if one ad request equals one impression.
  • Using IP as an identity signal without mentioning SSAI.
  • Reporting device counts as reach with no co-viewing or household caveat.
  • Assuming clicks exist as a CTV performance signal.
  • Proposing to store all bid requests indefinitely at full fidelity.

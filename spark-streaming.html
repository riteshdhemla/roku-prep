Spark, deeper

Streaming impressions without lying about time

Real-time pacing, frequency capping, and live dashboards all run on this. Structured Streaming questions are really questions about state and time — watermarks, output modes, and what happens to the data that arrives after you decided it wouldn't.

The execution model

Structured Streaming presents a stream as an unbounded table that grows, and your query as one that re-runs incrementally. The same DataFrame API, the same Catalyst optimiser.

Execution is micro-batch by default: the engine reads a bounded slice of the source, processes it as a normal Spark job, and commits. Trigger modes control the cadence — default (as fast as possible), fixed interval, availableNow (process everything available then stop, which is how you run a "streaming" job as a scheduled batch), and continuous processing (low-latency, experimental, limited operator support).

Checkpointing is mandatory and it holds three things: source offsets (what has been read), the state store (aggregation state), and a commit log. This is what makes restart correct — on restart the engine resumes from committed offsets rather than reprocessing or skipping.

The checkpoint is part of your schema

You cannot arbitrarily change a query and reuse its checkpoint. Adding a stateful operator, changing the aggregation keys, or changing the output schema can make the existing state unreadable. Plan for state migration — usually a new checkpoint plus a backfill — rather than discovering it during a deploy.

Event time, watermarks, and the completeness trade

Windowed aggregation must key on event time — when the impression happened — not processing time, or every number moves when the pipeline lags.

A watermark declares how late you're willing to wait: withWatermark("event_time", "30 minutes") tells the engine that once it has seen event time T, it will not accept events older than T minus 30 minutes. That assertion does two jobs: it lets a window be finalised and emitted, and it lets the engine drop the state for closed windows so memory doesn't grow forever.

The trade is direct and worth stating explicitly: a longer watermark means more completeness, more latency, and more state; a shorter one means faster results, less memory, and more dropped data. There's no setting that avoids the choice.

In CTV the late-data distribution is genuinely long-tailed — a device that loses connectivity mid-break can fire its quartile beacons much later, and SSAI vendors batch. So measure the actual distribution of ingest_time - event_time before choosing, and know what percentage the watermark excludes.

Window types: tumbling (fixed, non-overlapping — hourly impression counts), sliding (overlapping — trailing 1-hour count updated every 5 minutes), session (gap-based — viewing sessions). Sliding windows multiply state by the overlap factor, which is a common cause of state blowup.

Output modes and the sink

ModeEmitsRequiresUse
appendOnly rows finalised and never to changeWatermark for aggregationsWriting immutable results to a table
updateRows whose value changed this batchUpsert-capable sinkLive counters, pacing state
completeThe entire result table every batchBounded result sizeSmall dashboards only

complete mode never drops state — the whole result must be maintained — so it is unusable for anything with unbounded key space. That's a common trap: a query grouped by device_id in complete mode will grow until it dies.

foreachBatch is the workhorse for real sinks. It hands you each micro-batch as a normal DataFrame with a batch ID, so you can write with arbitrary logic — a MERGE into an Iceberg or Delta table, a write to a key-value store, or writes to two destinations. Combining the batch ID with an idempotent write is how you get exactly-once effect: re-processing a batch after failure overwrites rather than duplicates.

Joins in streams

Stream–static join. A stream joined against a static table (campaign metadata, creative dimensions). Cheap and stateless. The subtlety: the static side is re-read per batch depending on the source, so updates may or may not be picked up — know which, because a stale campaign dimension silently mislabels everything.

Stream–stream join. Joining impressions to quartile events, or bid requests to impressions. Both sides must be buffered, so both need watermarks plus a time-range condition on the join, or state grows unboundedly. The engine uses those to know when a row can no longer match and can be dropped.

impressions
  .withWatermark("imp_time", "30 minutes")
  .join(
    completions.withWatermark("comp_time", "2 hours"),
    expr("imp_id = comp_imp_id AND "
         "comp_time >= imp_time AND "
         "comp_time <= imp_time + interval 1 hour"),
    "leftOuter")

Outer joins have a specific gotcha: a non-matching row can only be emitted once the watermark guarantees no match will arrive, so outer join results are delayed by the watermark. If you need to know quickly that an impression never completed, a streaming outer join is the wrong instrument — that's a batch reconciliation.

State: the thing that actually breaks

Stateful streaming failures are nearly always state size or state skew.

  • Unbounded key space. Grouping by device_id with no watermark keeps state for every device ever seen. Always pair keyed aggregation with a watermark or explicit TTL.
  • The default state store is in-memory HDFS-backed, which holds state on heap and snapshots to checkpoint. The RocksDB state backend keeps state off-heap on local disk and is what you want for large state — it trades some latency for the ability to hold state far beyond heap.
  • State skew. A hot key concentrates state in one partition. Same shape as shuffle skew and the same remedies.
  • Checkpoint on object storage. S3-style stores have slow renames and eventual-consistency behaviours that make checkpointing expensive; per-batch checkpoint duration is a metric worth watching.
  • flatMapGroupsWithState when you need arbitrary custom state — a session tracker, a pacing accumulator — with explicit timeout handling. Powerful and the place people most often create leaks by never expiring state.

Monitoring: input rows per second vs processed rows per second (the backpressure signal), batch duration versus trigger interval (if duration exceeds the interval you're falling behind permanently), state row count and size, and source lag — Kafka consumer lag is the honest end-to-end freshness metric.

Pushback

Now defend it

Each of these is a real interrupt. Commit to an answer before you reveal — reading the model answer without having tried is how you end up recognising the material but not being able to produce it.

01
Build real-time campaign pacing: spend and impressions per campaign per minute, feeding a decisioning system.
Name the mode, the watermark, and the sink semantics.
What a strong answer covers

Source is the impression stream from Kafka, partitioned so ordering per campaign is preserved if we need it. The query is a windowed aggregation on event time — tumbling one-minute windows grouped by campaign — summing impressions and spend.

Watermark sized from the measured late-data distribution; for pacing I'd lean short, maybe 5–10 minutes, because a decisioning system needs current numbers more than complete ones, and the tail can be corrected by the batch pipeline later.

Output mode update, since pacing state is a mutable counter the decisioning system reads — not an append-only log.

Sink via foreachBatch writing an upsert keyed on (campaign, window) into a low-latency store, so re-processing a batch after failure overwrites rather than double-counts. That plus checkpointed offsets gives exactly-once effect.

Two things I'd add unprompted: the decisioning system should treat these numbers as approximately current and have a defined behaviour when the feed is stale — ideally falling back to a conservative pacing posture rather than assuming zero spend. And the batch pipeline recomputes the same numbers authoritatively, so the two must be reconcilable by construction, using the same metric definitions.

Then they push again

The stream is down for 40 minutes. When it restarts it processes the backlog in three minutes and the decisioning system massively overspends. What went wrong?

The decisioning system trusted a number it should have treated as suspect. Two separate failures, and I'd fix both.

The consumer side is the real bug. Pacing decisions were made during the outage against stale state without knowing it was stale. Every record written should carry a watermark or as-of timestamp, and the consumer must degrade when that timestamp is old — slowing delivery rather than assuming the campaign hasn't spent. Failing conservative is the right default when money is leaving the building.

The producer side amplified it. On restart the job processed 40 minutes of backlog in one or a few enormous micro-batches, so the counters jumped discontinuously. maxOffsetsPerTrigger bounds how much each batch consumes, which keeps batches uniform and the catch-up gradual, and also prevents the batch that OOMs on restart — a very common failure after any outage.

The general principle: a streaming pipeline will be down sometimes, so the correctness of the system has to survive its absence. Designing the consumer as if the stream is always current guarantees this class of incident.

02
You need to join impressions to completion events to compute completion rate in real time. What state does that require?
Both sides buffered, both watermarked, and outer-join timing.
What a strong answer covers

A stream–stream join, so both sides are buffered in state and both need watermarks plus a time-range condition, or state grows without bound.

Concretely: watermark impressions by however late impression beacons arrive, watermark completions more generously since they fire later by nature, and bound the join to a plausible window — a completion should arrive within the ad duration plus slack, so an hour is generous. State size is then roughly the volume of impressions within the watermark window on each side, which I'd estimate explicitly to size the state store, and I'd use RocksDB rather than the default backend at CTV volumes.

The important design caveat: to compute a rate, I need to know about impressions that never completed, which is a left outer join — and outer join results are only emitted once the watermark guarantees no match can arrive. So the non-completion signal is delayed by the full watermark.

Given that, I'd probably not compute completion rate this way. Counting impressions and completions as two independent windowed aggregations and dividing gives the rate with much less state and no outer join delay — at the cost of not being able to identify which impressions didn't complete. If the requirement is the metric, aggregate separately; if it's the per-impression record, do the join and accept the latency.

Then they push again

Product wants both: the live rate and the ability to drill into incomplete impressions.

Then I'd serve them from different layers rather than force one query to do both, which is usually the right shape when latency and completeness requirements diverge.

Streaming does the two independent aggregations and publishes the live rate — cheap, low state, seconds fresh. That's the number on the live dashboard.

Batch does the full join hourly against the raw logs, producing the per-impression completion record with the drill-down. It has the luxury of a much longer completeness window, so it's also more accurate, and it becomes the authoritative source.

This is the standard two-speed shape, and the thing that makes it work rather than confuse people is being explicit about which number is which. The live rate will not exactly match the batch rate, and if that difference is discovered rather than announced, trust in both collapses. So: label the live figure as provisional, show the as-of time, and make the batch figure the one that appears in anything anyone is held to.

03
Your streaming job's batch duration is creeping up over days. Nothing changed in the code.
Slow growth over time points at one thing above all.
What a strong answer covers

Gradual growth with static code almost always means state growth. Something is accumulating that isn't being expired.

Candidates, in order of likelihood:

  • A stateful operator without a watermark, or with one that doesn't actually bind — grouping by a high-cardinality key like device ID keeps a row per device forever.
  • flatMapGroupsWithState with no timeout configured, or a timeout that isn't being hit because the key stops receiving events and nothing triggers expiry.
  • Growing key space that is legitimate but unbounded — new campaigns accumulate and old ones are never removed from state.
  • Checkpoint overhead: as state grows, snapshotting to object storage takes proportionally longer, which shows up as batch duration even when the compute is unchanged.

I'd confirm from the streaming query metrics — state row count and state size per batch are exposed directly, and if they're rising monotonically that's the answer without further investigation. If state is flat, I'd look at source lag and input volume instead, since gradual traffic growth also produces this shape.

Then they push again

State is flat. Input volume is flat. Batch duration is still climbing.

Then it's environmental rather than logical, and I'd look outside the query. The strongest candidate is the sink or the checkpoint location degrading — if we're writing into a table that's accumulating files without compaction, each write's commit gets slower as metadata grows, and the streaming job pays that on every batch. That's a very common cause and it looks exactly like this: everything about the job is constant and it gets slower anyway.

Other candidates: the checkpoint directory accumulating old files and slowing listing; a downstream store that's slowing under its own growth; cluster-level noisy neighbours or storage throttling as our total footprint grows; or the small-files problem on a stream–static join's static side, where re-reading a dimension table gets slower as that table accumulates.

The diagnostic move is to break the batch duration into its phases — the streaming metrics separate planning, query execution, and commit — because that immediately says whether we're spending the extra time computing or committing, and those point in completely different directions.

Say it in sixty seconds
  1. Structured Streaming = unbounded table, micro-batch execution, mandatory checkpoint holding offsets, state, and commits.
  2. Aggregate on event time; the watermark trades completeness against latency and bounds state.
  3. append needs a watermark; update suits mutable counters; complete never drops state and is only for small results.
  4. foreachBatch plus an idempotent upsert keyed on batch ID gives exactly-once effect.
  5. Stream–stream joins need watermarks on both sides and a time-range condition; outer join emission is delayed by the watermark.
  6. State growth is the usual failure; use RocksDB for large state, watch state size and source lag.
What a weak answer sounds like
  • Using processing time for windowed aggregation.
  • A stateful query with no watermark or TTL.
  • complete output mode on an unbounded key space.
  • Claiming exactly-once without naming idempotent writes.
  • No position on what the consumer does when the stream is stale.
